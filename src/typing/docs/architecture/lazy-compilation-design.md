# Lazy Citizen Compilation

This doc `lazy-compilation-design.md` tracks moving struct/interface/impl compilation off the eager loops in `compiler.rs::evaluate` and onto the same lazy model functions already use.

## Design (human-only)

All functions, structs, interfaces, and impls are to be compiled lazily.

 * Callsites/use-sites will resolve-solve them, which shouldn't require us to have previously completed compiling them.
 * When they are used, their compilation is added to a queue, to be done later.

There should not be a loop in compiler.rs that loops over all visible functions/structs/interfaces/impls.

This clears the way towards LSP support later, where the LSP tells us only to compile one particular item, and we can do just that, instead of compiling everything. We don't support that and LSP yet, but this is a step toward that.

A non-exported, uncalled function/type is never compiled, so its type errors go unreported. This is fine for now.

### Illuminate vs Resolve vs Compile, and the Queue

At the start of compilation, we don't know anything about anything. For example, in:
```
import ship_library.make_ship;
struct Foo { }
func main() {
  println(make_ship().engine.fuel);
}
```
we actually haven't compiled anything yet. We know that there exists something called a "make_ship", and something called a "Foo", but we don't know anything about them. We also don't know anything about `Engine`.

When the compiler first wants to know something about "make_ship", it finally fetches initial information about it. That's "illumination".

**Illumination** means to discover:

 * Its AHT, from a `.valen` file, or generated by a macro, or generated by the rust interop layer.
 * For a struct/interface, its outer environment, into coutputs.template_id_to_postparsed_function/struct/interface/impl.

However we are not yet _compiling_ it; we're not yet turning its AHT into typed VAST. We don't queue something's compilation until we've tried to use it (until we've tried to "resolve" it).

**Resolving** means to figure out _how to use_ something. It means:

 * For functions, figure out its entire prototype, in the use-site's terms.
 * For structs, figure out its generic parameters and members, in the use-site's terms.
 * For interfaces, figure out its generic parameters, in the use-site's terms.
 * For impls, figure out its generic parameters and struct and interface, in the use-site's terms.

(Note that we can break up "resolved" into various granularities in the future. For exmaple, we might want a struct's generic parameters but not yet its members.)

Note that we haven't actually _compiled_ the target's body into typed VAST yet. However, whenever we resolve something, we enqueue it to be later compiled. There is one deterministic queue, for all different kinds of items. Eventually, we pop something off the queue to "compile" it. 

**Compiling**, in the context of the typing pass, means to compile something's definition, in its own terms (with placeholders for its generic parameters).

 * For functions, this means figuring out its body, if it's a function.

Things should only be compiled once. When something is popped off the queue, we'll check if it's already been compiled.

### Structs/Interfaces

`precompile_struct`/`precompile_interface` also happens lazily. We should think of these as establishing an environment, almost like a lazy import statement.

A struct's members are learned synchronously at resolve (knowing each member's type, the way a function resolve learns its parameter and return types) so a use-site that needs the members never awaits the struct's deferred compile. Members are part of a struct's "signature" so to speak.

### Roots

compiler.rs seeds the queue with all `exported` items.

Tests can pass a flag that forces compilation of specific roots even when unexported. A test uses it to compile a non-exported func, and LSP will later use it to compile a single item.

`main` should always be exported, so it is always a root and needs no forced-root flag. If you see a test that doesn't write `exported` in front of main, that's a problem, and that test should be fixed.

### Impls

Use-sites enqueue impl compiles. For example, in:
```
struct Spaceship { }
impl IFlying for Spaceship;
interface IFlying { }
exported func main() {
  let s = Spaceship();
  let i IFlying = s;
}
```
The `let i IFlying = s` will check if we can upcast a Spaceship to an IFlying, and in so doing it will attempt to resolve all impls in Spaceship's outer-env (file) and in IFlying's outer-env (file).

### compile_itables runs whenever the queue is empty, perhaps multiple times

`compile_itables` looks at all abstract functions and impls, and enqueues anything that's missing. For example, if someone defines an abstract function on an interface, `compile_itables` will resolve all the override functions for the various structs that impl that interface.

It will run whenever the queue is empty, until it has nothing more to enqueue.

## Design Proposals

## Details

- (Design: Illuminate) Illuminate (`precompile_struct`/`precompile_interface`) is synchronous, not queued: the seam is `get_outer_env_for_type` in `compiler_outputs.rs`, which on a miss illuminates the type, memoizes, and returns — mirroring `get_or_create_postparsed_function` in `compiler.rs`.
- (Design: one queue) The two current deferred queues (`deferred_function_compiles`, `deferred_function_body_compiles`) unify into one queue holding all kinds; `resolve_*` enqueue their denizen, and the single drain loop dispatches per kind, producing e.g. the `StructDefinitionT`/`InterfaceDefinitionT`.
- (Design: Roots, S5) The export phase in `evaluate` seeds the queue by resolving each exported item — function, struct, interface, and standalone `export … as …` — enqueuing its compile; a caller-supplied forced-root list (S5) additionally seeds named non-exported denizens; every other denizen is pulled in transitively as those bodies resolve their callees and types.
- (Design: Impls) An upcast or edge lookup enqueues impl compiles: resolving `s` to an `IFlying` walks every impl in the sub-citizen's and super-interface's outer envs (files) and enqueues each.
- (Design: no eager loop) Each citizen's deferred compile runs its own `check_defining_conclusions_and_resolve` inline as it finishes; there is no separate batch resolution phase.
- (Design: compile_itables) The tail of `evaluate` is a fixpoint: drain the queue, then run `compile_i_tables` — which resolves the missing override functions for each impl of an interface's abstract functions, enqueuing them — and repeat until `compile_i_tables` enqueues nothing.
- (Design: Structs/Interfaces) `evaluate_maybe_virtuality` in `function_compiler_middle_layer.rs` must force the interface's precompile before it reads `lookup_sealed` — e.g. `get_outer_env_for_type(interface_template)` on the id it already computes — because the sealed-flag read is otherwise the one validation path that never touches the interface's env.
- (Design: Callsites) The three sites that harvest a citizen's function bounds by iterating its compiled inner env — `get_reachable_bounds`, `check_defining_conclusions_and_resolve`, `look_for_override` — instead take the bounds from the citizen's resolve-solve output (already registered by `add_instantiation_bounds`) or re-derive them from the postparsed header rules, so a use-site never forces the citizen's compile.
- (Design: Structs/Interfaces) Sharedness and `weakable` are read from precompile-time state, not the compiled definition: the sharedness sites use a `type_name_to_sharedness` accessor and impl compile reads `weakable` from the postparsed AST.
- (Design: Structs/Interfaces) The get-or-precompile seam moves off `CompilerOutputs` onto `Compiler` (it needs `self` + `&mut coutputs` + `global_env`); `global_env` is stored on `CompilerOutputs`, and the miss branch precompiles only `StructTemplate`/`AnonymousSubstructTemplate`/`InterfaceTemplate` ids, `vfail`-ing on placeholder/array/impl/closure ids that stay eagerly declared.
- (Design: one queue) The queue dedups by id, and a per-citizen/per-impl finished-set (mirroring `finished_deferred_function_compiles`) stops recompiling a drained denizen; the `mark_deferred_*` head-equality asserts collapse into one kind-dispatching drain.
- (S6) A struct's members are produced at resolve, synchronously — resolving each member's declared type to a `KindT`, the way a function resolve produces its param/return coords — so the members-reading sites (expression/pattern/macros/closure) read those resolve-produced members and never await a compile. Learning a member's type does not compile that member's type.

## Discussed examples and test cases

### Upcast enqueues impls from both the sub-citizen's and super-interface's files

Protects the rule that an upcast walks both files, not just the sub-citizen's (today `get_parents` walks only the sub-citizen's). Put the impl in the *interface's* file, not the struct's:

```
// spaceship.vale
struct Spaceship { }
// flying.vale
interface IFlying { }
impl IFlying for Spaceship;
// main.vale
exported func main() {
  s = Spaceship();
  i IFlying = s;   // upcast must find the impl in flying.vale
}
```

If only the sub-citizen's file were walked, the impl would be missed and the edge/itable would be absent.

### Mutually-recursive structs resolve without awaiting a compile

Protects S6: learning a struct's members needs only its members' *types*, not their compiles, so a cycle terminates.

```
struct A { b B; }     // A owns a B
struct B { a &A; }    // B borrows an A (a reference breaks the cycle)
exported func main() { a = A(B(...)); }
```

Resolving `A` learns member `b` has type `B` by resolving `B` to its `StructTT` id — it does not compile `B` — so there is no unbounded recursion and no await.

### A non-exported, uncalled helper compiled only via the forced-root flag

Protects S5 and the reachable-only rule. A non-exported `helper` that nothing calls appears in the output *only* when the forced-root flag names it; with an empty flag it is never compiled and its errors go unreported. (`main` is always exported, so it is a root without the flag — the flag is for LSP and non-`main` items.)

### Abstract method outside an unsealed interface (sealed-before-virtual)

Protects the illuminate-before-`lookup_sealed` fix.

```
interface IFlying { }                    // not sealed
func fly(virtual self &IFlying) void { } // abstract method declared outside IFlying
```

Compiling `fly` must illuminate `IFlying` before reading its sealed flag, so it emits `AbstractMethodOutsideOpenInterface` rather than panicking on an absent flag.

## Background

### Self-evident from the code

- `evaluate` in `compiler.rs` runs eager phases in order: precompile loop, compile loop, defining-conclusions resolution phase, impl compile phase, function compile phase, exports, i-tables, then the deferred function drain loop.
- `resolve_struct_layer` in `struct_compiler_generic_args_layer.rs` reads only the postparsed AST (`get_postparsed_struct`) and the declaring env; it never reads the compiled definition or the outer/inner env, then mints a `StructTT` id plus instantiation bounds.
- `precompile_struct`/`precompile_interface` in `struct_compiler.rs` call `declare_type`, `declare_type_sharedness`, (interfaces) `declare_type_sealed`, and `declare_type_outer_env`; the outer env holds the citizen's methods and siblings.
- `get_outer_env_for_type` in `compiler_outputs.rs` is a total accessor read by `overload_resolver`, `compiler_solver`, `impl_compiler`, `edge_compiler`, `function_compiler`, `expression_compiler`, and by `compile_struct_layer`/`compile_interface_layer` themselves.
- Functions' lazy model: `get_or_create_postparsed_function` in `compiler.rs` enqueues `DeferredActionT::EvaluateFunction`, drained by the loop near the end of `evaluate`; the top-level function loop still eagerly evaluates every top-level function.
- `precompile_interface` sets `interface_name_to_sealed` early so a virtual function compiled before the interface's body can check whether the interface is sealed.
- The deferred machinery currently has two queues, `deferred_function_compiles` and `deferred_function_body_compiles` (`compiler_outputs.rs`); `compile_i_tables` in `evaluate` runs before either is drained.
- The interface sealed flag has exactly one reader: `lookup_sealed` in `compiler_outputs.rs` (panics on a miss), called only by `evaluate_maybe_virtuality` in `function_compiler_middle_layer.rs` when validating an abstract method declared outside its interface. That path resolves the interface via `resolve_interface_layer` (postparsed AST only) and never calls `get_outer_env_for_type`, so today only the eager precompile pass guarantees the flag is present.
- The dormant `is_root_function`/`is_root_struct`/`is_root_interface` in `compiler.rs` encode the historical root set: a function is a root if its name is `main`, or it has `Export`, or it has `Extern`; a citizen is a root if it has `Export`.
- `get_parents` in `impl_compiler.rs` (the upcast/`is_descendant` path) walks only the sub-citizen's outer env plus the calling env and calls `resolve_impl`, not `compile_impl` — it never walks the super-interface's file and enqueues no impl compile.
- Every `declare_*`/`add_*` writer in `compiler_outputs.rs` asserts "not already declared/defined", encoding today's once-per-denizen visit; `mark_deferred_function_compiled`/`_body_compiled` assert the popped key is its queue's head.
- `make_extern_function` (`function_compiler_core.rs`) runs only while an extern function is header-compiled, so an extern that is never compiled never reaches `function_externs`.
- Array types are precompiled unconditionally by `compile_static_sized_array`/`compile_runtime_sized_array` in `evaluate`, independent of any seeding.
- The citizen inner env (`type_name_to_inner_env`, read via `get_inner_env_for_type` in `compiler_outputs.rs`) is declared during body compile (`compile_struct_layer`/`compile_interface_layer`) and holds the citizen's function bounds as `Rune -> Prototype(FunctionBound)` entries — the same data `add_instantiation_bounds` registers from the resolve solve's `rune_to_bound`, before any compile.
- Three sites read another citizen's inner env for its bounds during a *different* denizen's solve, each assuming the target is already compiled: `get_reachable_bounds` (`templata_compiler.rs`, call resolve), `check_defining_conclusions_and_resolve` (`infer_compiler.rs`, define path), and `look_for_override` (`edge_compiler.rs`, i-tables). Body-compile sites additionally read `StructDefinitionT.members` via `lookup_struct` (construction, member access, drop, closures); `make_struct_members` in `struct_compiler_core.rs` produces those from the postparsed members resolved against the struct's env.
- Sharedness lives in `type_name_to_sharedness` at precompile time, and `weakable` lives on the postparsed AST, yet several sites read them off the compiled definition via `lookup_struct`/`lookup_interface` (`struct_compiler_get_sharedness`, `kind_is_implicitly_cloneable`, `function_compiler_core`, impl compile).

### Undocumented

- Resolve is already independent of compile; the dependency that forces precompile to run first is method/overload resolution reading the type's outer env, not resolve itself.
- The two kinds of laziness differ: precompile must be synchronous because the env is needed at the call, while compile can be deferred because the definition is only read when assembling `HinputsT`.
- Learning a struct's members means knowing each member's type — a resolve-time computation like a function's signature — not compiling those member types; so it need not await any compile, and a struct that only appears as a member's type stays uncompiled until separately resolved.
- The design vocabulary maps to code as: illuminate = `precompile_struct`/`precompile_interface` (register the citizen's outer env); resolve = `resolve_struct`/`resolve_interface` and function-prototype resolution (the signature in the use-site's terms); compile = `compile_struct`/`compile_interface`/function-body compile (the whole denizen in its own placeholder terms, landing in `HinputsT`).
