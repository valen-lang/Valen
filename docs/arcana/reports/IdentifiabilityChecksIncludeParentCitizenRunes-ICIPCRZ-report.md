# Accuracy report: Identifiability Checks Include Parent Citizen Runes (ICIPCRZ)

Audited against the working tree on 2026-09-06. Source: git:790fc183:Frontend/docs/arcana/IdentifiabilityChecksIncludeParentCitizenRunes-ICIPCRZ.md (recovered, deleted from tree; Scala-era doc)

## Verdict
The mechanism this doc describes is alive and confirmed in the ported Rust code, just with Scala→Rust renames throughout (camelCase→snake_case, `.scala` files→`function_scout.rs`/`overload_resolver.rs`) and one terminology drift: there is no longer a distinct "identifiability check" pass or `checkIdentifiability` function — the postparser simply builds `generic_params` (own + body + parent, parent last) once in `scout_function`, and that combined list *is* what downstream code treats as identifying/generic runes, with no separate validation step. Every other claim — parent runes appended at the end, `RuneParentEnvLookupSR` stripped for citizen-internal methods but preprocessed into `InitialKnown`s elsewhere, and the explicit-callsite container-template-arg channel feeding `InitialKnown`s into the solve — is TRUE in current code. Core idea intact, wording about a discrete "check" is stale. Recommendation: migrate into docs/arcana as a proper Z-suffix doc, folding in the current file/function names (function_scout.rs, overload_resolver.rs) and dropping the "identifiability check" framing in favor of "generic_params construction."

## Suggested text
Parent-citizen methods (`Vec<T>.with_capacity(...)`) never write the citizen's generic params on their own header, but the callsite always supplies them via qualified container syntax (`Vec<int>.with_capacity(42i64)` binds `T=int` on the prefix, not the method). The postparser's `scout_function` therefore appends the parent citizen's generic params onto the method's own `generic_params` list, always last (per @PRIIROZ), so the rest of the compiler treats them as legitimate identifying/generic runes for that method — modeling the real input channel instead of leaving them unaccounted for. The companion mechanic: a `RuneParentEnvLookupSR` rule (emitted when a rule references a rune declared only in an enclosing/parent scope) is stripped from a parent-citizen method's rule array before any solve, because the constraint solver has no notion of a parent environment to look anything up from and panics (`vwat`) if one reaches it unpreprocessed. Two channels supply the value instead: (1) for calls through the explicit-callsite container-template-arg syntax, the typing pass pre-solves the container's template args into `InitialKnown`s and threads them into the method's own solve (`overload_resolver.rs::attempt_candidate_banner`); (2) for other paths (e.g. function bounds) that still carry a `RuneParentEnvLookupSR`, the call site looks the rune up directly in the calling environment and folds it into `InitialKnown`s before invoking the solver — the same "must-know-runes-from-above" contract documented under @MKRFA (docs/arcana/Generics.md).
