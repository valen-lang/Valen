# Accuracy report: container-chain fold (title unknown) (PRIIROZ)

Audited against the working tree on 2026-09-06. Source: git commit d3507636 (message only — no doc file, no `definition_text`); corroborated by comments at src/postparsing/expressions.rs:310, src/postparsing/function_scout.rs:906, src/typing/function/function_compiler_core.rs:484, and by docs/architecture/simplifier-design.md:695,756.

## Verdict
PRIIROZ names a two-part convention: (1) at scout/typing time, a citizen's (container's) generic parameters are appended *after* a method's own generic parameters when building `generic_params`/`template_args` — this part is TRUE and still live in three code sites. (2) at instantiation/wire-format time, Hammer (now `instantiator.rs`) was supposed to reshuffle a leaf extern step's trailing `numInherited` template args onto the parent step so Backend's `rustifySimpleId` sees `Vec<i32>::capacity` instead of `Vec::capacity<i32>` — this half is **not implemented** in the current tree: the only code that ever did it is commented out (src/instantiating/instantiator.rs:1684-1699), the field carrying the count is hardcoded to `0` under `rust_interop` (src/instantiating/rust_interop/mod.rs:190, comment: "The extern is born here, complete, with rustc's real symbol"), and the one test that exercises the reshape is `unimplemented!()` and `#[ignore]`d for an unrelated reason (src/integration_tests/tests/hammer_tests.rs:426-427). docs/architecture/simplifier-design.md:695 and :756 still describe this reshuffle as something Hammer's `translate` actively does — that's now false for the current mechanism, since Rust externs get their real name from rustc's own symbol resolution rather than a template-arg splitAt. Recommendation: migrate the scout-time ordering half into docs/arcana (it's real, well-corroborated, and cited from 3+ live sites), but the migrated text must drop the Hammer-reshuffle claim or mark it explicitly as dead/superseded-by-rust_interop; also flag docs/architecture/simplifier-design.md:695,756 to the maintainer as stale.

## Suggested text
Container-chain fold (parent-generics-last convention): when a method belongs to a citizen (struct/interface), the citizen's own generic parameters are always appended *after* the method's own generic parameters, both when scouting a method's `generic_params` (src/postparsing/function_scout.rs) and when building an `OutsideLoadSE`'s per-part explicit template args for a chained load like `HashMap<int,str>.create_and_fill(...)` (src/postparsing/expressions.rs). This ordering is load-bearing wherever a citizen's generic arity needs to be split back off a combined arg list — e.g. `GenericParametersInheritance::num_inherited_generic_parameters`, computed at typing time in src/typing/function/function_compiler_core.rs, records how many trailing args are inherited so a downstream consumer can move them back onto the citizen step of a wire-format id. As of the rust_interop path, that downstream reshuffle is not needed for Rust-backed externs — rustc's own `symbol_name` supplies the real link name (src/instantiating/rust_interop/mod.rs) — so the split-back-out consumer in the instantiator is currently dead code and the one test covering it is unimplemented/ignored; anyone reviving a non-rust_interop extern-naming path needs to re-wire that consumer, not just re-derive the count.
