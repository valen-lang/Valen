# Accuracy report: Must Know Runes From Above (MKRFA)

Audited against the working tree on 2026-09-06. Arcana section: docs/arcana/Generics.md:438 ("## Must Know Runes From Above (MKRFA)")

## Verdict
The core mechanism (Case 1/Case 2, PostParser tracking known runes via `IEnvironmentS`/`all_declared_runes`, `RuneParentEnvLookupSR`, and the per-call-site preprocessing fold) is accurate and confirmed live. But the closing "⚠ Known architectural smell" paragraph is stale: it claims "the value solver's handler for `RuneParentEnvLookupSR` is a silent no-op that conceals violations" and frames replacing it with `vwat()` as a queued near-term fix — that half of the fix is already done. `src/typing/infer/compiler_solver.rs:1100` is a `panic!("vwat: RuneParentEnvLookupSR should have been MKRFA-preprocessed...")`, not a no-op. Only the other half of the queued work (extracting the duplicated fold into a shared `InferCompiler` helper) is still outstanding — the fold is still hand-duplicated at 5 sites (overload_resolver.rs:437, array_compiler.rs:88/208/415, pattern_compiler.rs:69). This is the same drift already caught and reported for the sibling doc @ECSIIOSZ (docs/arcana/reports/EachCallSiteIsItsOwnSolve-ECSIIOSZ-report.md), which even names compiler_solver.rs:1100 as the current enforcement point uncited by MKRFA.

None additional beyond what's covered above — the known sites (array_compiler.rs, overload_resolver.rs, pattern_compiler.rs) all still carry the live, correctly-functioning inline fold; they're just not routed through a shared helper as the doc's "queued" fix would have it.

## Suggested rewrite
Replace the closing paragraph of the section with:

> **⚠ Known architectural smell — partially addressed.** MKRFA is a **recurring-bug pattern with partial enforcement.** The contract still lives in prose comments cross-referencing the "MKRFA" tag, not in types — but the value solver's handler for `RuneParentEnvLookupSR` is no longer a silent no-op: it now panics with `vwat("RuneParentEnvLookupSR should have been MKRFA-preprocessed before reaching the solver")` (src/typing/infer/compiler_solver.rs:1100), so any future caller that forgets preprocessing crashes immediately instead of producing a misleading downstream "couldn't solve" error. Three `ArrayCompiler` methods sat in violation for ~4 years before the symptom surfaced (April 2026, via the `Borrowing toArray` AfterRegions test); those are fixed. What's still outstanding is the deduplication: the preprocessing fold is still hand-duplicated at five call sites (overload_resolver.rs, array_compiler.rs ×3, pattern_compiler.rs) instead of living in a single `InferCompiler` helper — extracting it into one place, so new sites get the contract for free, is queued in `docs/historical/mkrfa-protocol-leak.md`.
