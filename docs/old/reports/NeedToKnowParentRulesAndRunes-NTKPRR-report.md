# Accuracy report: Need To Know Parent Rules and Runes (NTKPRR)

Audited against the working tree on 2026-09-06. Arcana section: docs/old/Compiler/Templar/Environments, Templatas, and Parent Entries.md:55 ("## Need To Know Parent Rules and Runes")

## Verdict
The section is a Scala-era design musing that walks through *why* the compiler needs to remember a generic struct's rules (e.g. `Key = Ref(_, Kind(imm))`) when resolving calls to an inner/nested struct's constructor (`Map:Entry(...)`), using the "Scout stage" (rune collection) and "Templar" (rule solving) split. The worked example depends on a nested-inner-struct declaration syntax (`struct Entry { ... }` declared lexically inside `struct Map<Key, Value> { ... }`, referenced at the call site as `Map:Entry(...)`) that no longer exists anywhere in the current grammar, test corpus, or docs — grep for nested-struct declarations and `:Entry`-style call syntax across src/ and docs/ (excluding docs/old and docs/convos) turns up nothing. Renaming aside (Scout → still `scout_arena.rs`/parsing front end, Templar → typing pass), the concrete mechanism this section reasons about (propagating a parent struct's rune rules through nested-inner-struct constructor calls) is not something the current compiler does, because the language feature it hinges on is gone. The general principle "generic resolution needs access to enclosing scopes' rules" survives in spirit in the current environment/templata-resolution code, but the section's specific claims and example are about a retired feature, not a description of live behavior. Recommendation: leave in docs/old (do not migrate — the worked example is obsolete and would mislead; delete is also reasonable given zero live citations, but leaving it as historical context costs nothing).
