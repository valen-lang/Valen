# Accuracy report: Adding Constructors To Environments (ACTE)

Audited against the working tree on 2026-09-06. Arcana section: docs/old/Compiler/Templar/Environments, Templatas, and Parent Entries.md:359 ("## Adding Constructors To Environments (ACTE)")

## Verdict
The core idea — a struct's constructor is registered as a sibling entry in the same (outer) environment the struct itself lives in, so overload resolution finds it via an argument's type environment — is still true in FrontendRust, and the "sibling" terminology survives verbatim (`get_struct_sibling_entries_struct_constructor`, `sibling_entries`, `all_outer_entries` in src/typing/citizen/struct_compiler.rs). But the doc's contrast — drop/`__call` are placed "in the struct's environment itself" as something different from the constructor's sibling placement — has drifted: in the current code drop is generated by the identical sibling-entry mechanism as the constructor (`get_struct_sibling_entries_struct_drop`, chained into the same `all_outer_entries`), so there is no longer a meaningful difference in placement between drop and constructors. The closing claim ("We can also add the constructor function under a parent interface's name, to facilitate sealed interface constructors") has no matching code today — no such parent-interface registration was found. Recommendation: migrate a corrected, updated version into docs/arcana/ (the sibling-entry mechanism is real, current, and uncited) rather than leaving the stale drop/constructor distinction in docs/old.

## Suggested rewrite
Some functions (e.g. drop and struct constructors) are registered as "sibling entries" of the struct/interface itself, merged into the struct's own outer environment (`struct_compiler.rs`'s `all_outer_entries`, built from `internal_method_entries` chained with `sibling_entries`). Because that outer environment is exactly what `overload_resolver::get_outer_env_for_type` pulls in for each argument's type, a function registered there is automatically a candidate whenever a value of that type is passed as an argument — this is why declaring `func drop(...)` or a synthesized constructor next to a struct makes it callable via ordinary overload resolution, without special-casing constructor or drop calls. The constructor can't simply be an "internal method" of the struct the way a regular method is, since the struct's own type isn't an argument to its own constructor call — so it's synthesized as a sibling top-level entry under the same id instead. (The doc's older claim that a constructor could also be registered under a parent interface's name to support sealed-interface constructors has no current implementation and should be dropped or re-verified before migrating.)
