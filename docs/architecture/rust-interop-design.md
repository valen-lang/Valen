# Rust Interop

Living design doc for how the Valen compiler interops with Rust. This is the primary authority on the subject. This doc is the authoritative place for the design's intent. If there are any conflicts or inaccuracies, raised them to the architect.

## Design (human-only)

The Valen compiler, often referred to as `valenc`, is actually three possible programs:

 * `valenc` only compiles pure Valen code, and has no Rust interop.
    * Example: `valenc -o ./nobiliav NobiliaV/src/main.valen`
 * `valenc-rs` is a fork of the rust compiler, statically linking in `valenc` code.
    * The user never runs this directly.
    * Example: `valenc-rs /home/user/.cargo/bin/rustc --crate-type bin --crate-name nobiliav --edition 2021 src/bin.valen`
 * `valen` is a program that generates a Cargo project and calls `RUSTC_WORKSPACE_WRAPPER=valenc-rs cargo build` on it, which tells `cargo` to use `valenc-rs` instead of `rustc`.
    * Example: `valen build`
    * Example: `valen run --manifest-path Valen.toml`

valen : valenc :: cargo : rustc. `valen build` is the cargo-like orchestrator, `valenc`/`valenc-rs` are the `rustc`-like compilers.

Absolute invariants for interop mode:

 1. A pure-Rust crate must compile byte-identically to vanilla rustc. (@PRCCBIVRZ)
 2. Cross-language inlining optimization is an absolute requirement.
 3. There will never be anything with `repr(C)` between Valen and Rust. `repr(C)` should appear nowhere in Valen-Rust interop.
 4. The compiler doesn't _depend_ on anything in `rustc` to compile pure Valen code.
    * This is also enforced by the `rust_interop` feature flag; most tests run with it disabled, and expect a working binary in the end.

Deviations from vale-rust-interop-architecture.md:
 * They call things "vale", we call them "valen".
 * We use three programs (`valenc`, `valenc-rs`, `valen`). They had two programs (`valec` and `valec-rs`). We split their `valec-rs` into our `valenc-rs` and `valen`.
 * `Oracles.rust` is a non-`Option` `&dyn RustOracle` with a panicking fake.
 * The `lib.rs` used by the typing pass is generated after parsing, and it only includes generated `use` statements corresponding to what `import`s the parser found in the `.valen` files.
 * The `lib.rs` used after the typing pass is generated after and informed by the typing pass's outputs. `valenc-rs` emits the stub after its typing pass (from `HinputsT`). It is NOT calculated from the parser output and NOT pre-generated by `valen`. Reason: Valen is semantically but not syntactically Rust-shaped, so the same Valen syntax projects to different Rust depending on typed facts a parser can't see (struct vs class, `&Foo in g`/`mut(g)` vs `&T`/`&mut T`, linearity, etc).
 * A Valen **library** compiles in **two rustc passes** (pass 1 types the `.valen` and emits the stub; pass 2 compiles the stub for codegen and a typed rmeta), where the architecture assumes one rustc per crate. Only one Valen typing pass runs (pass 2 reuses the cached `HinputsT`). A **binary** stays one pass, since nothing consumes it.
 * We **parse the `.valen` before starting rustc**, to get the rust imports for the generated crate root; `after_expansion` then only postparses and types. The architecture parses inside `after_expansion`.
 * Overrides install via config.override_queries, not a custom backend (see @OWTHACBZ).
 * `valenc-rs` looks at the main file extension (`.valen` or `.rs`) to know whether a crate is a Valen crate or a pure-Rust crate. For pure-Rust crates, it uses the default config, doesn't install any Valen machinery, and compiles just like vanilla rustc. This upholds invariant @PRCCBIVRZ, see @PRCCBIVRZ. The other thing that upholds @PRCCBIVRZ is that all of the patches we made to our linked-in rustc fork _default_ to the old behavior.


### Valen Wraps Rustc Which Runs Valen

In interop mode, we:

 1. Determine if it's a Valen crate. If not, just start up rustc and let it run, don't do the below steps.
 2. Since it's a Valen crate, install query overrides and consumer_fill_modules.
 3. Parse the Valen crate to scout out imports.
 4. Fire up a rustc as a framework and let it drive the rest of the compilation pipeline, and it calls out to us whenever Valen things come up.

Specifically, `src/typing/rust_interop/driver/main.rs` will do something like:
```rs
if filename ends in .valen {
  let callbacks = ValenRustInteropCallbacks {};
  ... // Parse
  ...
  rustc_driver::run_compiler(&rustc_args, &mut callbacks);
} else {
  let callbacks = NoopCallbacks {};
  rustc_driver::run_compiler(&rustc_args, &mut callbacks);
}
```
which runs rustc, and tells it the `callbacks` with which it should call into the Valen compiler.

Currently, we **statically link** rustc into valenc, because we use a patched rustc fork. One day, we might upstream those patches and we can then dynamically link against rustc nightly and retire the fork.

That `&mut callbacks` is a **ValenRustInteropCallbacks** (old names "LangCallbacks"/"DrivenCallbacks").

`ValenRustInteropCallbacks` has these three methods:

 * `config`, called shortly after rustc starts up, in which we install queries (explained below).
 * `after_expansion`, called before rustc's instantiation pass, to call valen's postparsing+typing passes (parsing happens before we invoked rustc).
 * `after_analysis`, called after typecheck+borrowck before codegen, so we can cache valen typing pass outputs.

`after_expansion` sets a thread_local `VALENC_RUSTC_INTEROP_STATE` struct (elsewhere still called "DRIVER_STATE") for:
 * `per_instance_mir` to read during instantiation
 * `consumer_fill_modules` to read during backend codegen


#### ValenRustInteropCallbacks::config installs the query overrides and consumer_fill_modules

Our config callback looks like this:
```rs
fn config(&mut self, config: &mut rustc_interface::Config) {
  // Install the query overrides
  config.override_queries = Some(valen_override_queries);

  // The fill_extra_modules hook is a fork-patched process-global (not a query, not on the backend trait).
  rustc_codegen_llvm::set_fill_extra_modules_hook(consumer_fill_modules);
}
```

#### valen_override_queries installs query overrides

We point the `override_queries` function pointer at our `valen_override_queries` which installs the query overrides:
```rs
pub fn valen_override_queries(_session: &Session, providers: &mut Providers) {
  providers.queries.per_instance_mir = lang_per_instance_mir;
  let _ = DEFAULT_COLLECT_AND_PARTITION.set(providers.queries.collect_and_partition_mono_items);
  let _ = DEFAULT_DEDUCED_PARAM_ATTRS.set(providers.queries.deduced_param_attrs);
  providers.queries.collect_and_partition_mono_items = lang_collect_and_partition_mono_items;
  providers.queries.deduced_param_attrs = lang_deduced_param_attrs;
  // layout_of and cross_crate_inlinable TBD
}
```

In provide, specifically we install:
 * `per_instance_mir`, which will be called during instantiation.
 * `collect_and_partition_mono_items` which will trigger instantiating then removes valen functions from the list of things their backend should emit.
 * `deduced_param_attrs` which removes some function information that rustc incorrectly derives about our valen functions.
 * `layout_of` and `cross_crate_inlinable` will come soon.

#### Query `collect_and_partition_mono_items` triggers instantiation pass

Our `collect_and_partition_mono_items` function pointer points at this function:
```rs
fn lang_collect_and_partition_mono_items<'tcx>(
  tcx: TyCtxt<'tcx>,
  key: (),
) -> MonoItemPartitions<'tcx> {
  // Get rust's default collect_and_partition_mono_items implementation...
  let upstream = DEFAULT_COLLECT_AND_PARTITION.get().expect(...);
  // ...and call it.
  let MonoItemPartitions { codegen_units: upstream_cgus, all_mono_items: reachable, .. } = upstream(tcx, key);
  ... // If no __VALEN_STUBS_MARKER, just return the above.

  // Populate the filtered_cgus with new CGUs that don't contain any valen items
  let mut filtered_cgus: Vec<CodegenUnit<'tcx>> = ...
  // Assemble new result.
  MonoItemPartitions { codegen_units: tcx.arena.alloc_from_iter(filtered_cgus), all_mono_items: reachable, }
}
```
Note that the `upstream(tcx, key)` is actually **triggering the entire instantiation pass** (which also calls `per_instance_mir` a bunch of times, btw).

#### Query `per_instance_mir` does instantiation for a Valen function

This runs during the instantiation pass. It mainly does three things:
 * Remember the mangled name of the function, for the backend to use later.
 * Call into the Valen instantiator for this export.
 * Build the MIR body of the fake function that we'll give back to rustc.

```rs
fn lang_per_instance_mir<'tcx>(
  tcx: TyCtxt<'tcx>,
  instance: Instance<'tcx>,
) -> Option<&'tcx Body<'tcx>> {
  let def_id = instance.def_id();

  // Skip anything that's not defined in Valen.
  if !is_valen_codegen_target(tcx, def_id) {
    return None;
  }

  // e.g. "__valen_myExportedValenFunction"
  let stub_name = tcx.item_name(def_id).to_string();
  // e.g. "myExportedValenFunction"
  let export_name = stub_name.strip_prefix("__valen_").unwrap_or(&stub_name).to_string();

  let state: &DriverState = ... // Get ptr to VALENC_RUSTC_INTEROP_STATE

  // Remember the rustc-mangled name of the exported function, for the backend to use.
  let symbol = tcx.symbol_name(instance).name.to_string();
  state.record_export_symbol(&export_name, symbol);

  // Call the Valen instantiator for this export, and gather the newly encountered rust things.
  let requests = state.collect_new_rust_requests(tcx, &export_name);
  let rust_deps = requests.iter().filter_map(|r| r.dep).collect();

  ... // Logging

  // Build the fake MIR body, mentioning the encountered rust things.
  let body = build_dependency_body(tcx, instance, &rust_deps);
  Some(tcx.arena.alloc(body))
}
```

See src/instantiating/docs/architecture/instantiating-rust-interop-design.md for more on this.

#### Query `deduced_param_attrs` removes incorrect valen function information

DeducedParamAttrs is e.g. whether a function is readonly. rustc usually calculates these during codegen.

We don't want rustc to calculate these for Valen functions, because it would calculate them incorrectly (because we give it a fake function, after all).

So, we make it say that Valen functions don't have any DeducedParamAttrs, with our override:
```rs
fn lang_deduced_param_attrs<'tcx>(tcx: TyCtxt<'tcx>, def_id: LocalDefId) -> &'tcx [DeducedParamAttrs] {
  // If it's a Valen function, return empty attrs.
  if is_valen_codegen_target(tcx, def_id.to_def_id()) {
    return &[];
  }
  // Call default handler
  let default = DEFAULT_DEDUCED_PARAM_ATTRS.get().expect("default deduced_param_attrs not saved");
  default(tcx, def_id)
}
```

### Cargo Wraps All Of It
(or in other words: Cargo Wraps Valen Wraps Rustc Which Runs Valen)

Whenever someone runs `valen build`, it actually generates a cargo project and runs it.

`valen build` will, when invoked on a `Valen.toml` with any `[rust-dependencies]`:

 * Generate a `target/valen-build` folder, which contains:
    * `Cargo.toml`: workspace manifest: members, resolver="2", and profile overrides (panic="abort", opt-level, lto, etc.)
    * `Cargo.lock`
    * `.cargo/config.toml`: rustflags, panic=abort
    * `rust-toolchain.toml`: pins the fork toolchain (rustc-fork)
    * One subdir per Valen project (e.g. `my-valen-library`):
       * `Cargo.toml`: generated from `Valen.toml` (see below)
       * `build.rs`: toolchain check — errors if built without valenc-rs
       * `src/` which is a *copy* of the original `src` folder.
 * Invoke `RUSTC_WORKSPACE_WRAPPER=valenc-rs cargo build` on it.
    * `cargo` invokes `valenc-rs` **once per crate**.
      For a non-Valen crate:
       * Don't install the overrides nor consumer_fill_modules.
       * Just invoke rustc the normal way on this crate.
      For a binary, `valenc-rs` will be invoked like e.g. `valenc-rs /home/user/.cargo/bin/rustc --crate-type bin --crate-name my-valen-library --edition 2021 src/bin.valen`, and it will:
       * Run the parser.
       * Look at the parsed .valen files' rust imports (e.g. `import rust.std.vec.Vec;`)
       * Put these into a `bin.rs`:
          * All those imports, as rust imports (e.g. `use std::vec::Vec;`)
          * `fn main() { exit(__valen_main()) }`
          * `#[valen::emit_consumer_body] fn __valen_main() -> i32 { unreachable!() }`
       * Start up a `rustc` instance pointing at this `bin.rs`.
          * Run the postparser+typing passes (see src/typing/docs/architecture/typing-rust-interop-design.md), producing a typed Valen AST.
          * It will do the instantiating pass and backend, and generate these outputs:
             * Normal `rustc` compile outputs like the executable (linked), plus the Valen-emitted .o.
      For a library, `valenc-rs` will be invoked like e.g. `valenc-rs /home/user/.cargo/bin/rustc --crate-type lib --crate-name my-valen-library --edition 2021 src/lib.valen`, and it will:
       * Run the parser.
       * Look at the parsed .valen files' rust imports (e.g. `import rust.std.vec.Vec;`)
       * Put them all in a `lib.rs` file as rust imports (e.g. `use std::vec::Vec;`)
       * Start up a `rustc` instance via `rustc_driver::run_compiler`, pointing it at that `lib.rs`. This will make it load all those things into memory so we can query them.
          * Run the postparser+typing passes (see src/typing/docs/architecture/typing-rust-interop-design.md), producing a typed Valen AST.
       * Write that Valen AST to a cache.
       * Look at all the `exported` functions in the Valen AST, e.g. `exported func launch(ship &Ship)void { ... }`.
       * Generate rust equivalents for them, e.g. `pub fn launch(ship &Ship) { unreachable!(); }` and append them into the `lib.rs`.
       * Start up a **new** `rustc` instance pointing at this updated `lib.rs`.
          * Skip the typing pass this time, reuse the Valen AST from the cache.
          * It will do the instantiating pass and backend, and generate these outputs:
             * Normal `rustc` compile outputs like `.rmeta`, `.rlib`, Valen-emitted `.o`.
             * `target/valen-build/target/debug/valenc-stubs/my-valen-library/lib.rs` (or `bin.rs`). This **must** be after the typing pass, because one cannot compute the equivalent `lib.rs` for a Valen library.
 * Update `Valen.lock` from `Cargo.lock`.


#### Generating Cargo.toml from Valen.toml

A `Valen.toml` will look like:

```toml
[project]
name = "nobiliav"
version = "0.1.0"
edition = "experimental"

[valen-dependencies] # other Valen projects
geometry = { path = "../geometry" }

[rust-dependencies] # crates.io — valenc-rs only
winit = "0.30"
wgpu  = "22"
glam  = "0.29"

[[bin]]
name = "nobiliav"
source = "src/main.valen"
```

And it will generate a corresponding `target/valen-build/Cargo.toml` like:

```toml
[package]
name = "nobiliav"
version = "0.1.0"
edition = "2021"

[dependencies]
# Copied from [rust-dependencies] (possibly with adjusted paths):
winit = "0.30"
wgpu  = "22"
glam  = "0.29"
# Copied from [valen-dependencies] (possibly with adjusted path):
geometry = { path = "../geometry" }

[[bin]]
name = "nobiliav"
path = "src/main.valen"   # the .valen — valenc-rs compiles it and emits the stub .rs to target/
```

The generated `Cargo.toml`'s `geometry = { path = "../geometry" }` might not be _exactly_ the same as the one in `Valen.toml`; the `Valen.toml` one could have been anything but `Cargo.toml` will always have `../`, because it points to the _generated_ copy.

We'll also generate a `target/valen-build/Cargo.lock` from `Valen.lock`.

### On Whether to Have a Custom Backend (@OWTHACBZ)

Having cross-language inlining is a requirement. That means that Valen backends need to generate into the same LLVM context/module as rustc, before it's fed to rustc's optimize/ThinLTO pass.

There are two ways to do this:

 * Fork rustc to expose a `fill_extra_modules` process-global hook. Small, proven working, less risk of churn, but it's more of a surgical hack.
 * Fork rustc so that CodegenCx/Builder/ModuleLLVM are `pub`, so a custom backend `ValenCodegenBackend` can do inline injection itself.

On upstreamability, respectively:

 * The `fill_extra_modules` approach is definitely not upstreamable as is. A process-global hook is just _bad_. However, if we could find a way to do that approach without a process-global hook, that could be potentially upstreamable.
 * The `ValenCodegenBackend` approach is more upstreamable than a process-global hook, but still somewhat bad (exposing private things isn't a good idea, so not _close_ per se). However, we would want to be sure of the final upstreamable shape before moving to this, because this fork would have much more drift/churn.

Both of these approaches would work in theory. Since the first one is working and would have less churn, we went with the first one. We could switch to something closer to the second one later if/when we want to upstream.

### Dynamic Dispatch

When we eventually support dynamic dispatch, we'll mostly fake it via a "dynamic dispatch adapter".

For example, if a Rust library has a function like this:
```rs
trait ARustTrait {
  fn trait_method(&self, i: i64) -> bool;
}
fn call_dyn_trait_method(fatptr: &dyn ARustTrait) -> bool {
  return fatptr->trait_method(42);
}
```

And a Valen program wants to call it like this:
```valen
import rust.my_rust_library.ARustTrait;
import rust.my_rust_library.call_dyn_trait_method;

struct MyValenStruct { }
impl ARustTrait for MyValenStruct;
func trait_method(self &MyValenStruct, i: i64) bool {
  return i < 73;
}

fn main() {
  mvs = MyValenStruct();
  result = call_dyn_trait_method(&mvs);
  print(result); // prints true
}
```

The `call_dyn_trait_method(&mvs);` is actually lowered to something like:
`call_dyn_trait_method(ARustTrait__DynAdapter<MyValenStruct>(&mvs));`

Where `ARustTrait__DynAdapter` is defined like this:
```rs
struct ARustTrait__DynAdapter<C: ARustTrait>(C);
impl<C: ARustTrait> ARustTrait for ARustTrait__DynAdapter<C> {
    fn on_tick(&self, w: &NobiliaWindow, input: FrameInput) { self.0.on_tick(w, input) }
}
```

In other words, **every Rust trait comes with an auto-generated `__DynAdapter`**.

Then, we can let Rust figure out all the vtable nonsense, we just have to instantiate the DynWrapper as if it's a normal class, and we're good.

## Design Proposals

S1. `Oracles.rust` is a non-optional `&dyn RustOracle` in interop builds, not an `Option`. The configurations with no real oracle — pure-Valen-semantics tests and the owned-mode standalone compilation — pass a panicking `RustOracle` fake, which is safe because none of them run `import rust` and so none ever consult it. Standalone (non-interop) builds keep no oracle field at all.

S2. A Valen **library** compiles in **two passes** inside `valenc-rs`: pass 1 uses an imports-only crate root to type the `.valen` and emit the typed stub + `.vale-cache` (no codegen); pass 2 compiles that typed stub into the rlib and a correctly-typed rmeta (per_instance_mir + `fill_extra_modules`, reusing pass 1's `HinputsT`). A Valen **binary** compiles in **one pass**: a crate root of imports + marker + the fixed `main`/`__valen_main` root, typed in `after_expansion`, then codegen. A library needs two passes because its stub can only be built from `HinputsT`, which exists only after a first rustc pass (typing needs the oracle); a binary needs no typed rmeta because nothing consumes a binary.

## Background

### Self-evident from the code

 * Nothing makes rustc discover Valen; Valen drives rustc. Our binary statically links rustc (`#![feature(rustc_private)]` + `extern crate rustc_driver`, `src/typing/rust_interop/driver/main.rs`) and calls `rustc_driver::run_compiler(&args, &mut callbacks)` (`harness.rs:727`, `driver/main.rs:185`) inside `catch_with_exit_code`. rustc then calls the `Callbacks` methods (`config` first) on the struct we passed it.
 * The `fill_extra_modules` hook is the one channel not on the `Callbacks` contract: a fork-patched process-global set via `rustc_codegen_llvm::set_fill_extra_modules_hook` (`harness.rs:526`).
 * rustc calls into Valen through six points today. `DrivenCallbacks::config` (`src/typing/test/rust_interop/harness.rs`) installs them: `override_queries = valen_override_queries` plus `set_fill_extra_modules_hook(consumer_fill_modules)`.
 * `valen_override_queries` (`src/instantiating/rust_interop/mod.rs`) overrides three rustc queries: `per_instance_mir` (drives our instantiator), `collect_and_partition_mono_items` (strips our `#[valen::emit_consumer_body]` stub bodies before LLVM codegen), and `deduced_param_attrs` (returns `&[]` for those stubs).
 * `consumer_fill_modules` (`src/instantiating/rust_interop/mod.rs`) is the `fill_extra_modules` fork-patch hook, called before rustc's `start_async_codegen`; this is where our backend emits Valen bodies into rustc's module.
 * Two callbacks structs exist for two jobs: `ValenCallbacks` (`src/typing/rust_interop/driver/main.rs`) runs typing only and returns `Compilation::Stop`; `DrivenCallbacks` (`src/typing/test/rust_interop/harness.rs`) drives codegen and returns `Compilation::Continue`. `ValenRustInteropCallbacks` is the intended unified name for both.
 * The opposite direction (Valen reads facts from rustc, the oracle seam) is a larger set of ordinary query reads, not overrides: `tcx.layout_of` + `tcx.fn_abi_of_instance` for aggregate ABI (`compute_struct_layouts` / `compute_extern_abi` in `src/instantiating/rust_interop/mod.rs`), `tcx.symbol_name` for single-symbol naming, and `module_children` / `fn_sig` for imports.
