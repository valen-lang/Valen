# Rust Interop

Living design doc for how the Valen compiler interops with Rust. This is the primary authority on the subject. This doc is the authoritative place for the design's intent. If there are any conflicts or inaccuracies, raised them to the architect.

## Design (human-only)

The Valen compiler, often referred to as `valenc`, is actually three possible programs:

 * `valenc` only compiles pure Valen code, and has no Rust interop.
    * Example: `valenc -o ./nobiliav NobiliaV/src/main.valen`
 * `valenc-rs` is a fork of the rust compiler, statically linking in `valenc` code.
    * The user never runs this directly.
    * Example: `valenc-rs /home/user/.cargo/bin/rustc --crate-type bin --crate-name nobiliav --edition 2021 src/bin.valen`
 * `valen` is a program that generates a Cargo project and calls `RUSTC_WORKSPACE_WRAPPER=valenc-rs cargo build` on it, which tells `cargo` to use `valenc-rs` instead of `rustc`.
    * Example: `valen build`
    * Example: `valen run --manifest-path Valen.toml`

valen : valenc :: cargo : rustc. `valen build` is the cargo-like orchestrator, `valenc`/`valenc-rs` are the `rustc`-like compilers.

Absolute invariants for interop mode:

 1. A pure-Rust crate must compile byte-identically to vanilla rustc. (@PRCCBIVRZ)
 2. Cross-language inlining optimization is an absolute requirement.
 3. There will never be anything with `repr(C)` between Valen and Rust. `repr(C)` should appear nowhere in Valen-Rust interop.
 4. The compiler doesn't _depend_ on anything in `rustc` to compile pure Valen code.
    * This is also enforced by the `rust_interop` feature flag; most tests run with it disabled, and expect a working binary in the end.

Here is a list of deviations from vale-rust-interop-architecture.md. These items are authoritative, and they are where this doc intentionally overrules vale-rust-interop-architecture.md.

 * They call things "vale", we call them "valen".
 * We use three programs (`valenc`, `valenc-rs`, `valen`). They had two programs (`valec` and `valec-rs`). We split their `valec-rs` into our `valenc-rs` and `valen`.
 * `Oracles.rust` is a non-`Option` `&dyn RustOracle` with a panicking fake.
 * The `lib.rs` used by the typing pass is generated after parsing, and it only includes generated `use` statements corresponding to what `import`s the parser found in the `.valen` files.
 * The `lib.rs` used after the typing pass is generated after and informed by the postparser's and typing pass's outputs. `valenc-rs` emits the stub after its typing pass (from `HinputsT` and the postparseds (for groups/mutabilities)). It is NOT calculated from the parser output and NOT pre-generated by `valen`. Reason: Valen is semantically but not syntactically Rust-shaped, so the same Valen syntax projects to different Rust depending on typed facts a parser can't see (struct vs class, `&Foo in g`/`mut(g)` vs `&T`/`&mut T`, linearity, etc).
 * We compile a Valen crate in **two rustc passes** (pass 1 types the `.valen` and emits the stub; pass 2 compiles the stub for codegen and a typed rmeta), where the valen-rust-interop-architecture.md assumes one rustc per crate. Only one Valen typing pass runs (pass 2 reuses the cached `HinputsT` and postparseds (for groups/mutabilities)).
 * We **parse the `.valen` before starting rustc**, to get the rust imports for the generated crate root; `after_expansion` then only postparses and types. The architecture parses inside `after_expansion`.
 * Overrides install via config.override_queries, not a custom backend (see @OWTHACBZ).
 * `valenc-rs` looks at the main file extension (`.valen` or `.rs`) to know whether a crate is a Valen crate or a pure-Rust crate. For pure-Rust crates, it uses the default config, doesn't install any Valen machinery, and compiles just like vanilla rustc. This upholds invariant @PRCCBIVRZ, see @PRCCBIVRZ. The other thing that upholds @PRCCBIVRZ is that all of the patches we made to our linked-in rustc fork _default_ to the old behavior.
 * In our rustc fork, our `per_instance_mir` query doesn't declare `cache_on_disk_if { false }` anymore. `cache_on_disk_if { ... }` existing means "generate caching machinery". Its absence means "don't generate caching machinery". `cache_on_disk_if { key.is_local() }` would mean "generate cache machinery, and use it for local things". But `false` means "never save into the cache, never look in the cache". So, `cache_on_disk_if { false }` doesn't really make sense (we generate cache machinery, but then never use it). It's better to just leave it out.

If you see any inconsistencies between this doc and vale-rust-interop-architecture.md, and they aren't in the above list, please stop and flag/raise them to the architect.

### Valen Wraps Rustc Which Runs Valen

In interop mode, we:

 1. Determine if it's a Valen crate. If not, just start up rustc and let it run, don't do the below steps.
 2. Since it's a Valen crate, install query overrides and consumer_fill_modules.
 3. Parse the Valen crate to scout out imports.
 4. Fire up a rustc as a framework and let it drive the rest of the compilation pipeline, and it calls out to us whenever Valen things come up.

Specifically, `src/typing/rust_interop/driver/main.rs` will do something like:
```rs
if filename ends in .valen {
  let callbacks = ValenRustInteropCallbacks {};
  ... // Parse
  ...
  rustc_driver::run_compiler(&rustc_args, &mut callbacks);
} else {
  let callbacks = NoopCallbacks {};
  rustc_driver::run_compiler(&rustc_args, &mut callbacks);
}
```
which runs rustc, and tells it the `callbacks` with which it should call into the Valen compiler.

Currently, we **statically link** rustc into valenc, because we use a patched rustc fork. One day, we might upstream those patches and we can then dynamically link against rustc nightly and retire the fork.

That `&mut callbacks` is a **ValenRustInteropCallbacks** (old names "LangCallbacks"/"DrivenCallbacks").

`ValenRustInteropCallbacks` has these three methods:

 * `config`, called shortly after rustc starts up, in which we install queries (explained below).
 * `after_expansion`, called before rustc's instantiation pass, to call valen's postparsing+typing passes (parsing happens before we invoked rustc).
 * `after_analysis`, called after typecheck+borrowck before codegen, so we can cache valen typing pass outputs.

`after_expansion` sets a thread_local `VALENC_RUSTC_INTEROP_STATE` struct (elsewhere still called "DRIVER_STATE") for:
 * `per_instance_mir` to read during instantiation
 * `consumer_fill_modules` to read during backend codegen


#### ValenRustInteropCallbacks::config installs the query overrides and consumer_fill_modules

Our config callback looks like this:
```rs
fn config(&mut self, config: &mut rustc_interface::Config) {
  // Install the query overrides
  config.override_queries = Some(valen_override_queries);

  // The fill_extra_modules hook is a process-global (not a query) read by rustc's LLVM backend.
  rustc_codegen_llvm::set_fill_extra_modules_hook(consumer_fill_modules);
}
```

#### valen_override_queries installs query overrides

We point the `override_queries` function pointer at our `valen_override_queries` which installs the query overrides:
```rs
pub fn valen_override_queries(_session: &Session, providers: &mut Providers) {
  providers.queries.per_instance_mir = lang_per_instance_mir;
  let _ = DEFAULT_COLLECT_AND_PARTITION.set(providers.queries.collect_and_partition_mono_items);
  let _ = DEFAULT_DEDUCED_PARAM_ATTRS.set(providers.queries.deduced_param_attrs);
  providers.queries.collect_and_partition_mono_items = lang_collect_and_partition_mono_items;
  providers.queries.deduced_param_attrs = lang_deduced_param_attrs;
  // layout_of TBD
}
```

In provide, specifically we install:
 * `per_instance_mir`, which will be called during instantiation.
 * `collect_and_partition_mono_items` which will trigger instantiating then removes valen functions from the list of things their backend should emit, and marks the Valen-called Rust functions as globally visible.
 * `deduced_param_attrs` which removes some function information that rustc incorrectly derives about our valen functions.
 * `layout_of` may come soon.

`after_expansion` is called after the rustc typing pass.

and has various **read-only** methods to ask rustc about rust functions/structs/etc that the Valen code depends on. See src/typing/docs/typing-rust-interop-design.md for more.

#### Query `collect_and_partition_mono_items` triggers instantiation pass

Our `collect_and_partition_mono_items` function pointer points at this function:
```rs
fn lang_collect_and_partition_mono_items<'tcx>(
  tcx: TyCtxt<'tcx>,
  key: (),
) -> MonoItemPartitions<'tcx> {
  // Get rust's default collect_and_partition_mono_items implementation...
  let upstream = DEFAULT_COLLECT_AND_PARTITION.get().expect(...);
  // ...and call it.
  let MonoItemPartitions { codegen_units: upstream_cgus, all_mono_items: reachable, .. } = upstream(tcx, key);
  ... // If no __VALEN_STUBS_MARKER, just return the above.

  // Populate the filtered_cgus with new CGUs that don't contain any valen items.
  // Also, mark the Valen-called Rust functions as External linkage so they don't get cleaned up
  // by rustc's optimizations.
  let mut filtered_cgus: Vec<CodegenUnit<'tcx>> = ...
  // Assemble new result.
  MonoItemPartitions { codegen_units: tcx.arena.alloc_from_iter(filtered_cgus), all_mono_items: reachable, }
}
```
Note that the `upstream(tcx, key)` is actually **triggering the entire instantiation pass** (which also calls `per_instance_mir` a bunch of times, btw).

#### Query `per_instance_mir` does instantiation for a Valen function

This runs during the instantiation pass. It mainly does three things:
 * Remember the mangled name of the function, for the backend to use later.
 * Call into the Valen instantiator for this export.
 * Build the MIR body of the fake function that we'll give back to rustc.

```rs
fn lang_per_instance_mir<'tcx>(
  tcx: TyCtxt<'tcx>,
  instance: Instance<'tcx>,
) -> Option<&'tcx Body<'tcx>> {
  let def_id = instance.def_id();

  // Skip anything that's not defined in Valen.
  if !is_valen_codegen_target(tcx, def_id) {
    return None;
  }

  // e.g. "__valen_myExportedValenFunction"
  let stub_name = tcx.item_name(def_id).to_string();
  // e.g. "myExportedValenFunction"
  let export_name = stub_name.strip_prefix("__valen_").unwrap_or(&stub_name).to_string();

  let state: &DriverState = ... // Get ptr to VALENC_RUSTC_INTEROP_STATE

  // Remember the rustc-mangled name of the exported function, for the backend to use.
  let symbol = tcx.symbol_name(instance).name.to_string();
  state.record_export_symbol(&export_name, symbol);

  // Call the Valen instantiator for this export, and gather the newly encountered rust things.
  let requests = state.collect_new_rust_requests(tcx, &export_name);
  let rust_deps = requests.iter().filter_map(|r| r.dep).collect();

  ... // Logging

  // Build the fake MIR body, mentioning the encountered rust things.
  let body = build_dependency_body(tcx, instance, &rust_deps);
  Some(tcx.arena.alloc(body))
}
```

`per_instance_mir` is called from two directions:

 * From downstream, if downstream calls one of our `exported` functions (`exported func main`, `exported func moo<...>(...)`, etc).
 * From within our own crate, if we call a dependency's generic function (`rust_take_trait(my_valen_substruct)`).

See src/instantiating/docs/architecture/instantiating-rust-interop-design.md for more on this.

#### Query `deduced_param_attrs` removes incorrect valen function information

DeducedParamAttrs is e.g. whether a function is readonly. rustc usually calculates these during codegen.

We don't want rustc to calculate these for Valen functions, because it would calculate them incorrectly (because we give it a fake function, after all).

So, we make it say that Valen functions don't have any DeducedParamAttrs, with our override:
```rs
fn lang_deduced_param_attrs<'tcx>(tcx: TyCtxt<'tcx>, def_id: LocalDefId) -> &'tcx [DeducedParamAttrs] {
  // If it's a Valen function, return empty attrs.
  if is_valen_codegen_target(tcx, def_id.to_def_id()) {
    return &[];
  }
  // Call default handler
  let default = DEFAULT_DEDUCED_PARAM_ATTRS.get().expect("default deduced_param_attrs not saved");
  default(tcx, def_id)
}
```

### Cargo Wraps All Of It
(or in other words: Cargo Wraps Valen Wraps Rustc Which Runs Valen)

Whenever someone runs `valen build`, it actually generates a cargo project and runs it.

`valen build` will, when invoked on a `Valen.toml` with any `[rust-dependencies]`:

 * Generate a `target/valen-build` folder, which contains:
    * `Cargo.toml`: workspace manifest: members, resolver="2", and profile overrides (panic="abort", opt-level, lto, etc.)
    * `Cargo.lock`
    * `.cargo/config.toml`: rustflags, panic=abort
    * `rust-toolchain.toml`: pins the fork toolchain (rustc-fork)
    * One subdir per Valen project (e.g. `my-valen-library`):
       * `Cargo.toml`: generated from `Valen.toml` (see below)
       * `build.rs`: toolchain check — errors if built without valenc-rs
       * `src/` which is a *copy* of the original `src` folder.
 * Invoke `RUSTC_WORKSPACE_WRAPPER=valenc-rs cargo build` on it.
    * `cargo` invokes `valenc-rs` **once per crate**.
      For a non-Valen crate:
       * Don't install the overrides nor consumer_fill_modules.
       * Just invoke rustc the normal way on this crate.
      For a Valen crate, it will:
       * ...be invoked like:
          * For a binary:  `valenc-rs /home/user/.cargo/bin/rustc --crate-type bin --crate-name my-valen-library --edition 2021 src/bin.valen`
          * For a library: `valenc-rs /home/user/.cargo/bin/rustc --crate-type lib --crate-name my-valen-library --edition 2021 src/lib.valen`
       * Run the parser.
       * Create a `lib.rs` (yes, even if it's a binary). Put into it:
          * For each of the parsed .valen files' rust imports (e.g. `import rust.std.vec.Vec;`), a corresponding Rust import (e.g. `use std::vec::Vec;`).
       * Start up a `rustc` instance via `rustc_driver::run_compiler`, pointing it at that `lib.rs`. This will make it load all those things into memory so we can query them.
          * Run the postparser+typing passes (see src/typing/docs/architecture/typing-rust-interop-design.md), producing the postparseds and a typed Valen AST.
       * Write the Valen postparseds and typed AST to an in-memory cache (we remember the postparseds for its groups/mutabilities).
       * Delete the `lib.rs` from above.
       * Create a `bin.rs` (if binary) or `lib.rs` (if library). Add to it:
          * Everything from the above previous `lib.rs`.
          * `#![register_tool(valen)]`.
          * The `__VALEN_STUBS_MARKER` const.
          * `__valen_drop<T>`.
          * Some things for those calling into our crate:
             * (If a binary) add the `main` things, since the OS is calling into us:
                * `fn main() { exit(__valen_main()) }`
                * `#[valen::emit_consumer_body(...)] fn __valen_main() -> i32 { unreachable!() }`
             * (If a library) add things for downstream crates:
                * For each of the `exported` functions in the Valen AST, e.g. `exported func launch(ship &Ship)void { ... }`:
                   * Generate a Rust function for it, e.g. `#[valen::emit_consumer_body(...)] pub fn launch(ship: &Ship) { unreachable!(); }`. In rustc this becomes a DefId and a body (not a whole "function". More distributed, like an ECS entity). Later:
                      * Our `per_instance_mir` generates a different body, to trigger monomorphizations.
                      * Our `collect_and_partition_mono_items` removes the `Instance` from the list of functions that rustc should lower to LLVM.
                      * Our `fill_extra_modules` generates the LLVM function under the same mangled name.
                * For each type mentioned in those `exported` functions (like the `Ship` above):
                   * Generate a Rust declaration for it (e.g. `struct Ship { contents: __ValeOpaque<OID>, }`). It's fine that Rust's LLVM uses that while Valen's LLVM uses ours (as long as they agree on size + alignment + calling convention), because in LLVM types have no identity/symbol/linkage.
          * Things that will let us consume upstream Rust crates:
             * For each Valen `struct` that implements a Rust `trait` (for example the `Boat`/`ISailing` impl in Valen `boat = Boat(); read_sailing(&boat);` / Rust `fn read_sailing<S: ISailing>(s: &S)`):
                * Add to `lib.rs` a Rust equivalent of it (e.g. `struct Boat { contents: __ValeOpaque<OID>, }` and `impl ISailing for Boat { ... method placeholders here ... }`).
       * Start up a **new** `rustc` instance pointing at this updated `lib.rs`.
          * Skip the typing pass this time, reuse the Valen typed AST from the cache.
          * It will do the instantiating pass and backend, and generate these outputs:
             * (if a binary) Normal `rustc` compile outputs like the executable (linked), plus the Valen-emitted .o.
             * (if a library) Normal `rustc` compile outputs like `.rmeta`, `.rlib`, Valen-emitted `.o`.
             * (if a library) `target/valen-build/target/debug/valenc-stubs/my-valen-library/lib.rs` (or `bin.rs`). This **must** be after the typing pass, because one cannot compute the equivalent `lib.rs` for a Valen library.
 * Update `Valen.lock` from `Cargo.lock`.


#### Generating Cargo.toml from Valen.toml

A `Valen.toml` will look like:

```toml
[project]
name = "nobiliav"
version = "0.1.0"
edition = "experimental"

[valen-dependencies] # other Valen projects
geometry = { path = "../geometry" }

[rust-dependencies] # crates.io — valenc-rs only
winit = "0.30"
wgpu  = "22"
glam  = "0.29"

[[bin]]
name = "nobiliav"
source = "src/main.valen"
```

And it will generate a corresponding `target/valen-build/Cargo.toml` like:

```toml
[package]
name = "nobiliav"
version = "0.1.0"
edition = "2021"

[dependencies]
# Copied from [rust-dependencies] (possibly with adjusted paths):
winit = "0.30"
wgpu  = "22"
glam  = "0.29"
# Copied from [valen-dependencies] (possibly with adjusted path):
geometry = { path = "../geometry" }

[[bin]]
name = "nobiliav"
path = "src/main.valen"   # the .valen — valenc-rs compiles it and emits the stub .rs to target/
```

The generated `Cargo.toml`'s `geometry = { path = "../geometry" }` might not be _exactly_ the same as the one in `Valen.toml`; the `Valen.toml` one could have been anything but `Cargo.toml` will always have `../`, because it points to the _generated_ copy.

We'll also generate a `target/valen-build/Cargo.lock` from `Valen.lock`.

### Patches to rustc

We only needed to patch `rustc` to do two new things:

 * `per_instance_mir` query, so we could generate our own MIR per `Instance` during instantiation.
 * `fill_extra_modules` hook, so we could sneak a valenc-generated LLVM module into modules that rustc hands to the backend.

#### `per_instance_mir` query

This had three changes:

 * Declared with the rest of the queries in `rustc_middle/src/query/mod.rs`.
 * Default value (a closure returning `None`) in `rustc_mir_transform/src/lib.rs`.
 * `collect_items_of_instance` now consults `per_instance_mir` _first_, and if it returns `None`, falls back to the normal `tcx.instance_mir(instance.def)`. In `rustc_monomorphize/src/collector.rs`.

Note: `collect_items_of_instance` is called by `items_of_instance`.

#### `fill_extra_modules` hook

This one's much larger.

**Context:**

rustc coordinates what happens with modules. In this order:

 * rustc collects `Instance`s into CGUs. A CGU is a bunch of `Instance`s.
 * rustc asks the backend for any extra modules, via `fill_extra_modules`.
 * For each CGU (skipping some if doing an incremental build):
    * rustc gives the CGU to `backend.compile_codegen_unit(...)`, which:
       * For each `Instance` in that CGU, the backend:
          * Looks up the MIR and other metadata.
          * Uses it to lower the MIR and generate a complete LLVM function.
       * Assembles the LLVM functions into a `ModuleLlvm` LLVM module.
       * Returns it as a `ModuleCodegen<B::Module>`.
 * As each module is finished, rustc gives it to the backend for optimization.
 * When all modules are done, it gives them all to the backend for LTO.

Backends produce a list of modules. rustc doesn't know the type of a module, that's specified by the `WriteBackendMethods::Module` associated type.

`trait ExtraBackendMethods` is implemented by backends. rustc uses these methods to ask the backends various things. Valen only works with rustc's LLVM backend.

**Patch:**

In rustc, outside the backends:

 * Added `ExtraBackendMethods::fill_extra_modules` method, implemented by rustc's backends (well, only its LLVM backend really does anything with it) so rustc can ask its backend for any extra modules it would like to include.
    * Trait method in `rustc_codegen_ssa/src/traits/backend.rs`.
    * `codegen_crate` calls `backend.fill_extra_modules(tcx)` right before `start_async_codegen`. (`rustc_codegen_ssa/src/base.rs`)
 * Modified the loop that streams modules into the optimizers.
    * `extra_modules: Vec<ModuleCodegen<B::Module>>` threaded through `start_async_codegen` into `start_executing_work`. (`rustc_codegen_ssa/src/back/write.rs`)
    * Passes extra modules into `execute_optimize_work_item` (`start_executing_work` in `rustc_codegen_ssa/src/back/write.rs`)
    * `compiled_modules.extend(compiled_extra_modules)` to include them into the linker (`start_executing_work` in `rustc_codegen_ssa/src/back/write.rs`)

In rustc's LLVM backend:

 * Gave the LLVM backend a way for an outside tool to answer that method:
    * `FillExtraModulesHook` (the fn-pointer type), `FILL_EXTRA_MODULES_HOOK` global holding it, and `set_fill_extra_modules_hook` to set it (which `valenc-rs` calls)
    * `LlvmCodegenBackend`'s `fill_extra_modules` implementation, calls the hook. (`rustc_codegen_llvm/src/lib.rs`)

In rust's LLVM backend's ModuleLlvm:

 * `new` made `pub` so Valen can create one. (`rustc_codegen_llvm/src/lib.rs`)
 * `llcx_raw_mut` and `llmod_raw` for Valen to get the module's LLVMContext* and LLVMModule*. (`rustc_codegen_llvm/src/lib.rs`)

Q: Could have done this outside the LLVM backend?

A: Perhaps. We _might_ be able to make it work if Valen wrapped the LLVM modules in a `Vec<Box<dyn Any + Send>>` and gave that to rustc-outside-backends (`codegen_crate`), which then downcasts each box to `ModuleCodegen<B::Module>` before scheduling it. Even though that involves a downcast (and a run-time error), that might be better.


### Opacity

We don't want rust to see the contents of Valen structs.

#### Exported structs must be known to Rust, but not their innards

If a Valen crate exposes a type, like this `MyCollection`:

```
exported struct MyCollection<X> { inner_table: EpicList<X>; load_factor int; size int; bork: int; }

exported func foo<X>(ship &MyCollection<X>)void { ... }
```

We intentionally do NOT generate this: `struct MyCollection<X> { inner_table: EpicList<X>, load_factor: i32; size: i32, }`. That would be bad, because then we'd have to inform Rust about `EpicList` too. And `EpicList` might not even be expressible in Rust (like if it used comptime). Rust has no reason to see `EpicList` (it's not exported and it's never mentioned in any exported function) so Rust shouldn't be aware of it, ever.

Instead, we generate this: `struct MyCollection<X> { _d: PhantomData<*mut ()>, _p: PhantomPinned, _X: PhantomData<X> }`

When Rust tries to instantiate an e.g. `MyCollection<i64>`, our `layout_of` override can answer its questions about the type, and our `layout_of` can just look at the name "MyCollection" and look up data from the typing pass output about what we know is in there.


#### Valen structs implementing Rust traits must be known to Rust, but not their innards

Above, we talked about how `exported` structs make us generate a corresponding Rust struct.

There's another case that forces us to generate a corresponding Rust struct: impls.

**If a Valen struct implements a Rust trait, then it must have a Rust equivalent generated.**

So if we have this:

```
struct Ship<T> { ... }
impl<T> IFlying for Ship<T>;
func launch<T>(self &Ship<T>) { ... }

exported func main()void {
  s Ship<int> = ...
  dock_at_spaceport<Ship<int>>(s);
}
```

We need to generate this:

```
struct Ship<T> { _d: PhantomData<*mut ()>, _p: PhantomPinned, _T: PhantomData<T> }
impl<T> IFlying for Ship<T> { ... }
```

...because we need Rust to know that a `Ship` can be an `IFlying`.


#### Everything else shouldn't be known to rustc, and just use `__ValeOpaque<OID>`

If we don't `exported` the type, like this `PrivCollection`:

```
struct PrivCollection<X> { inner_table: EpicList<X>; load_factor int; size int; }
```

And then we use it with a Rust type:

```
exported func main() {
  v Vec<PrivCollection<int>> = ...
}
```

Then we don't want to generate even this: `struct MyCollection<X> { _d: PhantomData<*mut ()>, _p: PhantomPinned, _x: PhantomData<X> }`

Instead, we generate _nothing_ for that type.

Whenever we want to mention it in a Rust type, like a `Vec<PrivCollection<int>>`, and ask rustc to monomorphize that, we instead ask it to monomorphize `Vec<__ValeOpaque<6937445>>`.


That 6937445 is the "Opaque ID" (or "OID").

`__ValeOpaque` is defined:

```
pub struct __ValeOpaque<const OID: u128>(PhantomData<*mut ()>, PhantomPinned);
impl<const OID: u128> Drop for __ValeOpaque<OID> { ... }
```


Then, when rustc asks us for details about `__ValeOpaque<6937445>` (size, alignment, etc.), we look that up in our own private side table.


We do this for two reasons:

 * To avoid a "type declaration explosion" where we have to declare to Rust every single type in the Valen code and all of the Valen dependencies.
 * We want to keep as much as possible opaque to Rust, on principle, because more opacity = less coupling.

TODO: reconsider `__ValeOpaque`. The type declaration explosion wouldn't be _super_ massive... it would just be any type that's used in a Rust generic slot (the `Spork` in `Vec<Spork>`) and any type that impl's a rust trait (the `ValenStruct` in `take_rust_trait(my_valen_struct)`) (which we already do). And their fields don't have to be named, so there's no recursive infectious naming that has to happen.


### Comptime generic parameters become integers

We want to have `struct MyStruct<config: Config> { ... }` (where Config is a struct), and use it like `MyStruct<Config(42, "hello")>`.

In other words, comptime generic parameters, that aren't limited to Rust's const generics.


That isn't expressible to rustc. However, `MyStruct<35214534>` _is_ expressible to rustc.

So, our instantiator will have a map of e.g. 35214534 -> `Config(42, "hello")`. It's populated at instantiation time.


This is orthogonal to and unrelated to `__ValeOpaque`. This is a simple integer.


### Incremental Builds

#### Fingerprints

If a Valen library (called by a Rust crate) has this function:

```
exported func do_something<F: SomeValeTrait>(f F) {
  v Vec<F> = ...
  v.len();
}
```

And Rust called it with `do_something(42)`, our `per_instance_mir` will generate a synthetic MIR body that mentions `Vec<i32>::len`, so rustc knows to generate that.

However, what happens if we change the Valen source to this?:

```
exported func do_something<F: SomeValeTrait>(f F) {
  v Vec<F> = ...
  v.len();
  v.capacity();
}
```

Now this same `do_something` depends on `Vec<i32>::len` and `Vec<i32>::capacity`.

**This is a problem if rustc cached our `items_of_instance` results.**

`items_of_instance` is rustc's own query that answers "which functions/statics does this Instance reach?" (it calls+memoizes `per_instance_mir` and processes its results). And it is cached to disk.

So we need to invalidate the `items_of_instance` results if any of the Valen source changes.

We do that by putting a hash on everything we put in a generated `.rs`, inside our `emit_consumer_body` metadata, like this:

```
#[valen::emit_consumer_body(digest = "3f2a9c...")]
pub fn do_something<F: SomeValeTrait>(f: F) {
  unreachable!();
}
```

#### Warm-rebuild when nothing has changed

(Building on "Fingerprints" above)

If some of the Valen source has changed, then all of the fingerprints are now different, which will force rustc to re-invoke every `items_of_instance` and therefore every `per_instance_mir`.

However, if we rebuild _without changing any Valen source_, that means the fingerprints are all the same, and rustc skips invoking `items_of_instance`.

That's a problem, because then nothing invokes `per_instance_mir` (which does our monomorphizing), so Valen things aren't monomorphized, and then linking fails because it's all missing.


To help with this, we _re-invoke_ `per_instance_mir` ourselves, manually, just before codegen, no matter what. Either:

 * (warm rebuild) rust didn't invoke `per_instance_mir`, so this new call saves the day.
 * (cold rebuild) rust did invoke `per_instance_mir`, so this new call is redundant. valenc's instantiator memoizes everything normally, so this redundant call doesn't actually cause extra work.


### On Whether to Have a Custom Backend (@OWTHACBZ)

Having cross-language inlining is a requirement. That means that Valen backends need to generate into the same LLVM context/module as rustc, before it's fed to rustc's optimize/ThinLTO pass.

There are two ways to do this:

 * Fork rustc to expose a `fill_extra_modules` process-global hook. Small, proven working, less risk of churn, but it's more of a surgical hack.
 * Fork rustc so that CodegenCx/Builder/ModuleLLVM are `pub`, so a custom backend `ValenCodegenBackend` can do inline injection itself.

On upstreamability, respectively:

 * The `fill_extra_modules` approach is definitely not upstreamable as is. A process-global hook is just _bad_. However, if we could find a way to do that approach without a process-global hook, that could be potentially upstreamable.
 * The `ValenCodegenBackend` approach is more upstreamable than a process-global hook, but still somewhat bad (exposing private things isn't a good idea, so not _close_ per se). However, we would want to be sure of the final upstreamable shape before moving to this, because this fork would have much more drift/churn.

Both of these approaches would work in theory. Since the first one is working and would have less churn, we went with the first one. We could switch to something closer to the second one later if/when we want to upstream.

### Dynamic Dispatch

When we eventually support dynamic dispatch, we'll mostly fake it via a "dynamic dispatch adapter".

For example, if a Rust library has a function like this:
```rs
trait ARustTrait {
  fn trait_method(&self, i: i64) -> bool;
}
fn call_dyn_trait_method(fatptr: &dyn ARustTrait) -> bool {
  return fatptr->trait_method(42);
}
```

And a Valen program wants to call it like this:
```valen
import rust.my_rust_library.ARustTrait;
import rust.my_rust_library.call_dyn_trait_method;

struct MyValenStruct { }
impl ARustTrait for MyValenStruct;
func trait_method(self &MyValenStruct, i: i64) bool {
  return i < 73;
}

fn main() {
  mvs = MyValenStruct();
  result = call_dyn_trait_method(&mvs);
  print(result); // prints true
}
```

The `call_dyn_trait_method(&mvs);` is actually lowered to something like:
`call_dyn_trait_method(ARustTrait__DynAdapter<MyValenStruct>(&mvs));`

Where `ARustTrait__DynAdapter` is defined like this:
```rs
struct ARustTrait__DynAdapter<C: ARustTrait>(C);
impl<C: ARustTrait> ARustTrait for ARustTrait__DynAdapter<C> {
    fn on_tick(&self, w: &NobiliaWindow, input: FrameInput) { self.0.on_tick(w, input) }
}
```

In other words, **every Rust trait comes with an auto-generated `__DynAdapter`**.

Then, we can let rustc figure out all the vtable nonsense, we just have to instantiate the DynWrapper as if it's a normal class, and we're good.

## Design Proposals

S24. (For "Everything else shouldn't be known to rustc", which defines `__ValeOpaque<const OID: u128>(PhantomData<*mut ()>, PhantomPinned)`.) `__ValeOpaque` also carries a real `UnsafeCell<()>` field, so rustc sees it as `!Freeze` and emits no `readonly` on a `&__ValeOpaque<..>` parameter; Vale writes those bytes through aliasing group borrows while Rust holds the reference. Each marker declares honestly what rustc would otherwise assume: `UnsafeCell<()>` → `!Freeze`, `PhantomData<*mut ()>` → `!Send + !Sync`, `PhantomPinned` → `!Unpin`.

S23. The compiler never converts between `usize` and `int`/`i64`. A Rust API that takes a `usize` is reached through Rust code that does the `as usize` itself, e.g. `fn at<T>(v: &Vec<T>, i: i64) -> &T { &v[i as usize] }`.

S22. Valen has no `Deref` trait of its own; it uses Rust's. A method reached through a Rust type's shared `Deref` (`Vec<T>` → `[T]`) resolves at the callsite by rewriting the receiver to `deref(recv)`, one step, and only when the receiver is a Rust type. `DerefMut` is never followed: Valen has group borrowing and no mutable references.

S21. (For "Everything else shouldn't be known to rustc", which declares `const OID: u128`.) The OID is a 64-bit FNV-1a hash of the Valen type's humanized instantiated id. One function (`typeid`) is its only definition, used both when the instantiator lowers the type to `__ValeOpaque<OID>` and when the side table registers it.

S20. (Same section: "we look that up in our own private side table".) The side table maps an OID to the instantiated Valen struct it stands for. Size and alignment are computed when rustc asks: rustc sizes each member's Rust type with its own `layout_of`, and the members are laid out C-style in declaration order, which is the layout the Valen backend's LLVM struct of those members has. Valen computes no size of its own, so the two sides agree by construction.

S19. (For the override list under "Valen Wraps Rustc Which Runs Valen", whose `// layout_of TBD` and "`layout_of` may come soon" are stale.) `layout_of` is the fourth installed override. For a `__ValeOpaque<OID>` whose OID names an instantiated Valen struct, it answers that struct's real size and alignment as `BackendRepr::Memory` with one layout field per marker field, so a Valen struct crosses by value and sits in a `Vec` at its real stride. Every other type, including `&__ValeOpaque<..>`, `Option<__ValeOpaque<..>>`, and an OID that names nothing Valen instantiated, gets rustc's own answer.

S18. (For the human-only "Valen Wraps Rustc Which Runs Valen" section, which currently misstates the timing — it says `after_expansion` runs "after the rustc typing pass".) `after_expansion` — the callback where Valen's postparse+typing pass runs — is the earliest one with both a live `TyCtxt` and the imported dependency crates loaded and typed-queryable; it fires after rustc's macro expansion and name resolution but *before* rustc's own `analysis()` (the local crate's typecheck/borrowck), which Valen does not need because the generated stub bodies are `unreachable!()` and Valen typechecks the real Valen source itself. The typed Rust facts Valen reads all come from already-compiled dependency rlibs, so they are available the moment those crates are loaded.

S17. The `fill_extra_modules` hook is per-backend-instance state: `valenc-rs` constructs rustc's own `LlvmCodegenBackend` with its hook in a `pub extra_modules` field and installs it through `Config::make_codegen_backend`, the seam miri uses for `DummyCodegenBackend`. No process-global exists in the fork. rustc keeps driver behavior on `Config` and backend values, never on statics, so this is the shape an upstream reviewer accepts. Plan: `docs/handoffs/rust-interop-backend-hook-plan.md`.

S7. (Belongs under "Warm-rebuild when nothing has changed".) The manual re-invoke runs `per_instance_mir` for every export first, from our own sorted export list, then for everything else. Comptime values are computed during instantiation, so the table that says what `35214534` means is filled by the export that computed it, and everything rustc asks about a `MyStruct<35214534>` afterwards (`layout_of`, a callback) needs that entry to already be there. The full investigation behind this and the "Opacity" section's `__ValeOpaque` TODO — where the ID came from, what reads it, what a name replaces, what comptime forces, hash vs canonical bytes, drop glue — is `docs/handoffs/rust-interop-opaque-ids-report.md`.

S15. Add these to the deviations list:
 * Identity of a Valen type Rust can name (exported, or implementing a Rust trait) is the generated
   Rust struct's path, not a typeid. The struct carries the `PhantomData<*mut ()>` + `PhantomPinned`
   markers directly; it does not wrap a `ValeOpaqueType<HASH>` field. `__ValeOpaque<OID>` is only for
   a type Rust cannot name that sits in a Rust type slot. (Overrules §10.1, §10.6, §10.9's typeid table.)
 * A non-exported Valen type that implements a Rust trait gets a Rust struct, private to the stub
   crate, because an `impl` needs a `DefId`. (Overrules §9.4's "non-exports have no DefId"; keeps its
   intent, since no Rust source can name the struct.)
 * A comptime value used as a generic argument crosses as `const N: u128` on the named template,
   `MyStruct<35214534>`. Because comptime is value-only (§13.4), there is no "comptime-produced type"
   to hide behind an opaque; §10.7 Case 3 is Case 1 with a const argument. (Overrules §10.7 Case 3.)
 * Incremental builds: rustc serves `items_of_instance` from its cache on a warm build and never
   calls `per_instance_mir`, so our `collect_and_partition_mono_items` override re-fires it for every
   Valen item, exports first from our own sorted export list, and the pass-1 stub bakes a digest of
   the `.valen` source into every `emit_consumer_body` attribute so a source edit turns those nodes
   red. (§22 assumes rustc's incremental machinery is transparent to us; it is not.)
 * The `fill_extra_modules` hook constructs its own modules, with rustc's `ModuleLlvm::new`, and returns them; rustc owns them from then on. vale-rust-interop-architecture.md §4.2 patch 4 and Appendix C.4 instead have rustc lend modules to the hook through a `#[repr(C)]` allocator.

## Details

From the crate-root generation steps ("Create a `bin.rs` (if binary) or `lib.rs` (if library). Add to it: ..."): one function decides the Rust name of every Valen thing we put in the generated crate root (exported functions, structs that implement Rust traits, generated forwarder substructs, exported types). The stub generator calls it to write the declaration, and the instantiator calls it to look the item up again. Neither side may guess the name on its own, even when the Valen name looks usable as-is: some Valen names are not Rust identifiers (a struct called `type`, or the generated `<Interface>.anonymous`), and if the two sides ever disagree the lookup finds nothing and the call is silently dropped. Today the generated substruct's name comes from `anon_substruct_rust_name` in `typeid.rs`, while exported functions (`__vale_<name>`) and plain structs (the Valen name verbatim) are derived separately on each side; folding all three into that one function is part of the Next #4 cleanup in the handoff.

From the `collect_and_partition_mono_items` design (its force-External of the Valen-called Rust functions): after delegating to the saved default partitioner (which has already run `internalize_symbols`), the override sets `(Linkage::External, Visibility::Default)` on every surviving CGU item whose `symbol_name` matches a materialized `FunctionExternI.link_name`. It wins because the LLVM backend reads `data.linkage` directly; `Visibility::Default` (not `Hidden`) also keeps the item out of the internalize-candidate set. Match on `symbol_name`, never `def_path_str` (which ICEs in the partitioner's non-diagnostic context). Mirrors Harmonious's fork-free "Outcome A". Covers default (non-LTO) release; an LTO profile has a separate LLVM `internalize` pass (see Open Questions).

## Background

### Self-evident from the code

 * Nothing makes rustc discover Valen; Valen drives rustc. Our binary statically links rustc (`#![feature(rustc_private)]` + `extern crate rustc_driver`, `src/typing/rust_interop/driver/main.rs`) and calls `rustc_driver::run_compiler(&args, &mut callbacks)` (`run_driven_rustc` and `run_wrapper` in `src/typing/rust_interop/drive.rs`) inside `catch_with_exit_code`. rustc then calls the `Callbacks` methods (`config` first) on the struct we passed it.
 * The `fill_extra_modules` hook is the one channel not on the `Callbacks` contract: a fork-patched process-global set via `rustc_codegen_llvm::set_fill_extra_modules_hook` (`DrivenCallbacks::config`, `src/typing/rust_interop/drive.rs`).
 * `ModuleLlvm::new` (`rustc_codegen_llvm/src/lib.rs`, made `pub` by the fork) is the only constructor for an LLVM module in rustc's pipeline; `consumer_fill_modules` (`src/instantiating/rust_interop/mod.rs`) calls it for `vale_cgu` and returns the filled module to rustc via `ModuleCodegen::new_regular`.
 * rustc calls into Valen through seven points today. `DrivenCallbacks::config` (`src/typing/rust_interop/drive.rs`) installs them: `override_queries = valen_override_queries` plus `set_fill_extra_modules_hook(consumer_fill_modules)`.
 * `valen_override_queries` (`src/instantiating/rust_interop/mod.rs`) overrides four rustc queries: `per_instance_mir` (drives our instantiator), `collect_and_partition_mono_items` (strips our `#[valen::emit_consumer_body]` stub bodies before LLVM codegen), `deduced_param_attrs` (returns `&[]` for those stubs), and `layout_of` (`lang_layout_of`: sizes a `__ValeOpaque<OID>` from the Valen struct's members via `DriverState.opaque_universe`; everything else delegates to the saved default).
 * `lang_collect_and_partition_mono_items` (`src/instantiating/rust_interop/mod.rs`) also force-sets `(Linkage::External, Visibility::Default)` on each surviving item whose `symbol_name` matches a materialized `FunctionExternI.link_name` (the reified-leaf set on `DriverState.monouts`), so rustc's release internalize can't strand `vale_cgu`'s out-of-band references at link.
 * The reified leaf's symbol is `tcx.symbol_name` of its instance, stored as `FunctionExternI.link_name` when the leaf resolves in `resolve_new_requests` (`src/instantiating/rust_interop/mod.rs`) — the same string `symbol_name` yields for that item in the partitioner, so matching by symbol string is exact.
 * `consumer_fill_modules` (`src/instantiating/rust_interop/mod.rs`) is the `fill_extra_modules` fork-patch hook, called before rustc's `start_async_codegen`; this is where our backend emits Valen bodies into rustc's module.
 * Two callbacks structs exist for two jobs: `ValenCallbacks` (`src/typing/rust_interop/driver/main.rs`) runs typing only and returns `Compilation::Stop`; `DrivenCallbacks` (`src/typing/rust_interop/drive.rs`) drives codegen and returns `Compilation::Continue`. `ValenRustInteropCallbacks` is the intended unified name for both.
 * The opposite direction (Valen reads facts from rustc, the oracle seam) is a larger set of ordinary query reads, not overrides: `tcx.layout_of` + `tcx.fn_abi_of_instance` for aggregate ABI (`compute_struct_layouts` / `compute_extern_abi` in `src/instantiating/rust_interop/mod.rs`), `tcx.symbol_name` for single-symbol naming, and `module_children` / `fn_sig` for imports.

## Open Questions

 * Under an LTO release profile, does forcing the Valen-called Rust functions to External suffice, or is `@llvm.used` pinning of the leaves also required? Fat/thin LTO runs a *separate* LLVM `internalize` pass that force-External alone does not defeat. Force-External is verified only for default (non-LTO) release; the generated `[profile.release]` is intended to set `lto` (see "Generating Cargo.toml from Valen.toml"), so this needs settling before shipping release LTO.
 * Does the out-of-band `vale_cgu` + force-External model satisfy invariant 2 (cross-language inlining is an absolute requirement)? Valen's calls to Rust leaves are direct calls in a separate module that rustc's IR inliner never sees, so a leaf may link but not inline into a Valen caller (nor a Valen body into a Rust caller). The reference architecture fills bodies into rustc's own module (in-pipeline, before `start_async_codegen`) specifically to get this. Determine whether Valen must move to in-pipeline fill to honor invariant 2, or whether the current model achieves the inlining another way.
