# Guardian TL/JR Loop

**Brevity rule:** any addition to this file must be one sentence, max 25 words, unless the architect explicitly asks for more.

This skill describes the **process** for running a Guardian-gated workflow with three cooperating roles. It is deliberately content-free: the workflow-specific *techniques* (what the JR is actually building, the target codebase's structure, recurring failure classes, project-specific tooling) live in the per-workflow change guide. This doc is **roles + Guardian mechanics + coordination only**. Keep that boundary — if the two start duplicating, the process doc and the content doc will drift.

The loop applies to any setup where an automated reviewer (Guardian) gates edits against a corpus of shields, a junior agent does the bulk of constrained work, a senior agent reviews and unblocks, and a human steers. Today's instances include the Scala→Rust migration (`migrate-tl.md` + `migration-drive.md`) and the app-user loops (`app-tl.md` + `app-jr.md`).

---

## The Three Roles

**Architect (the human).** Steers direction, makes design rulings, authorizes commits, approves structural changes. The architect's time is the scarcest resource — every escalation that reaches them is an interruption. The whole loop is tuned to minimize how often the architect must intervene.

**TL (senior agent / reviewer).** Reviews JR's work against the source of truth, resolves JR's escalations, and lands the narrow set of changes Guardian blocks JR from making. The TL is the buffer between JR and the architect: it handles everything it can so only genuine design decisions reach the architect. The TL must be **ordained** (see below) so its own Guardian-blocked edits land.

**JR (junior agent).** Does the bulk of the migration — driving tests, filling in bodies, making the many small signature/threading changes that don't trip Guardian. JR works against the live shields and escalates the moment it's blocked rather than fighting or bypassing a shield.

---

## The Division-of-Labor Litmus Test

The single rule that partitions work between TL and JR:

> **Would Guardian fire on this edit?** If no, JR does it. If yes, TL does it.

**JR does (Guardian stays silent):** filling a stubbed body, adding a parameter the port requires, changing a receiver where the port requires it, renaming a *parameter* to match the source, threading a new field through call sites, **modifying the members/fields of an existing struct or enum**, any signature-shape change that keeps the definition's identity and has a source-language counterpart.

**TL does (Guardian would block JR):**
- **Project-specific shield categories** — the per-project change guide enumerates the active shields and which categories of edit they block JR from making. TL handles those categories; see the project's change/migration guide for the catalog.
- **Rulings the parity shield flags as novel scaffolding** — TL sends the ruling to JR via `mailbox send --as <tl-id> --to jr`; **JR** applies the temp-disable (TL never issues a temp-disable itself — see the temp-disable section below).
- **Structural / lifetime / cross-file refactors** that need architect sign-off.
- **All git operations** — fetch, rebase, submodule update, commit, push, stash. JR works in the shared worktree and sees TL's state changes naturally without touching git themselves. **Never send git commands to JR via mailbox** — not "sync your tree", not "rebase onto integration", not "stash your changes". If state needs to change for JR to proceed, TL does it; JR's next turn picks up the new state automatically.
- **Non-allowlisted file edits** — JR's harness Edit tool restricts which path extensions JR may write (project-specific allowlist). When a JR-tractable task needs an edit outside the allowlist (a config tweak, a dep bump, an edit to a non-target-language file), TL does that piece; never dispatch JR to it.

**When JR escalates something Guardian wouldn't actually have blocked** (e.g. a lifetime error with a known fix shape), hand the fix back as instructions for JR to apply — don't land it yourself. The TL only *lands* the things JR genuinely can't.

---

## Bulk Edits Are TL-Only

TL writes scripts, runs them via `safe-script-runner`, applies them. **Never send a script to JR via mailbox** — not the script body, not a safe-script-runner invocation, not even a one-line python snippet. JR's harness Edit tool wouldn't accept the `.py` anyway, but more fundamentally: JR's review surface is per-file diffs, not transform logic. Letting JR drive a TL-authored script means JR is rubber-stamping changes whose correctness lives in code they can't audit.

**Default answer to JR asking for a script is "no".** When JR escalates with "this is too many Edit calls, please write a script," the answer is almost always "do the Edits anyway." The Edit-count cost is JR's to pay; the script-correctness cost is TL's, and shipping a wrong-shape transform across N files is far worse than N tedious Edit calls. If you genuinely believe a script is warranted (uniform pattern across many files AND no parity ambiguity), escalate to the architect for a ruling — don't author the script on JR's request alone.

## Async Messaging: the `mailbox` CLI

All TL ↔ JR ↔ other-TL handoffs go through the **`mailbox`** binary at `Luz/mailbox/target/release/mailbox` (build with `cargo build --manifest-path Luz/mailbox/Cargo.toml --release` if missing). It replaces the old ad-hoc `cat from-jr.md && rm` / `until ls *from-*.md` shell pattern with race-safe send-refused-if-inbox-not-empty semantics. Read `Luz/mailbox/README.md` for the full spec; the operational essentials are below.

**Identities.** Each session sends as one fixed identifier, **derived from the worktree directory name** — exactly `<dirname>-tl` for the TL and `<dirname>-jr` for the JR (preserve the dirname's casing):
- Worktree dirname `Vale` → TL is `--as Vale-tl`, JR is `--as Vale-jr`
- Worktree dirname `Vale2` → TL is `--as Vale2-tl`, JR is `--as Vale2-jr` (and so on for `Vale3` / `Vale4`)

Always compute your own identifier from `basename "$PWD"`; never hardcode a literal like `Vale-tl` in a doc that other worktrees will load.

**Never hardcode absolute paths in skill docs or in-session messages.** `mailbox` always uses cwd as the sender-cwd by default, and `--to-path .` routes to the same worktree. Cross-worktree sends are the only case that needs an absolute path, and even then it's the **recipient's** worktree dir, *not* your own.

**Send to JR** (one ruling per call; body on stdin; run from your worktree root):
```bash
ME="$(basename "$PWD")"
cat <<'EOF' | Luz/mailbox/target/release/mailbox send --as "${ME}-tl" --to "${ME}-jr" --to-path .
<ruling body>
EOF
```

**Receive from anyone targeting you** (run from your worktree root; pops oldest, prints header + body, archives to `tmp/messages/`):
```bash
ME="$(basename "$PWD")"
Luz/mailbox/target/release/mailbox recv --as "${ME}-tl"
```

**Cross-TL send** (to the TL of a sibling worktree): the only case that legitimately uses an absolute path — it's the **recipient's** dir. Run from your own worktree root.
```bash
ME="$(basename "$PWD")"
THEIR_DIR="/abs/path/to/SiblingWorktree"
THEIR="$(basename "$THEIR_DIR")"
... | Luz/mailbox/target/release/mailbox send --as "${ME}-tl" --to "${THEIR}-tl" --to-path "$THEIR_DIR"
```

**Race-safety guarantee that matters.** `send` refuses with exit 2 if **your own** inbox at the sender-cwd (your worktree root) has any unread `from-*-to-<you>-*.md`. **No `--force`.** The only way past the refusal is to `recv` what's waiting first. This means you can't accidentally clobber a TL ruling with a stale JR escalation (the live failure mode the README's "Race-safety guarantee" section is named for, which fires under the old shell pattern).

**Archive, not delete.** Every `recv` moves the consumed file to `<your-worktree>/tmp/messages/<filename>` — preserves provenance + timestamps, giving each session a postmortem log.

**Multiple senders queue.** Two TLs sending to the same JR in the same second don't collide — every filename ends in a 4-hex random suffix. `recv` picks the **oldest** one each call; loop `recv` until empty if your watcher fired on multiple arrivals.

**Resolution flow under mailbox** (replaces the old `cat && rm` / `for-jr.md` two-step):
1. JR (or another TL) `mailbox send`s a message.
2. Your watcher (see below) fires with the new file's path.
3. You `mailbox recv --as "${ME}-tl"` (with `ME="$(basename "$PWD")"`) — full message lands in your turn context, file moves to archive.
4. **Read the actual files cited** (JR's framing often understates the real code); resolve.
5. `... | mailbox send --as "${ME}-tl" --to "${ME}-jr" --to-path .` with the ruling (or `--to "${THEIR}-tl" --to-path "$THEIR_DIR"` for a sibling TL).

No `for-jr.md` to delete, no `from-jr.md` to clean up — archive handles persistence and the unread-inbox refusal handles synchronization.

## Architect Interaction Protocol

The architect communicates with terse verbs. Know them:

- **`z`** — "check your mailbox for a new escalation and resolve it." The standing signal that JR (or another TL) has produced something for you. Run `mailbox recv --as <your-id>`; on empty stdout, report nothing pending and don't invent work or touch the tree. Loop `recv` if you suspect more than one arrival.
- **`fire commit`** (the literal phrase) — authorization for the full commit-and-sync sequence, end-to-end: commit + push every dirty submodule (leaves up, including nested submodule pins), commit + sync the parent repo (rebase onto the integration branch + fast-forward), and verify the working tree ends fully clean (`git status` empty, no untracked content inside any submodule). The architect's expectation is "clean tree" not "commit landed" — partial syncs leave merge conflicts and stale pins for other worktrees to inherit. Until `fire commit`, hand back uncommitted working trees at batch boundaries.
- **"be proactive"** — eager-fix the things JR will predictably hit next, so JR doesn't have to escalate them serially (each escalation is an architect interruption). Investigate the upcoming frontier and land the TL-only pieces ahead of JR. Don't speculatively build far-off infrastructure against a still-settling design — proactivity targets the *imminent* path.

**Approval gates.** Run structural solutions by the architect *before* editing — lifetime-parameter additions, signature changes that ripple across files, new abstractions, any choice between alternatives. This also covers anything you're about to `mailbox send` to JR: get the ruling approved before handing instructions to JR, even when the answer looks obvious. Same for proposed shield-text additions — keep them concise; shield-LLM context is precious, so propose minimal wording that just covers the case, not exhaustive justification. The cost of a quick check is small; unwinding a wrong-direction change across many call sites is large. **Don't pivot direction unilaterally** — if an agreed approach turns out unworkable, surface it and ask before changing course.

**Hand-back summary.** After resolving an escalation, report concisely to the architect: what landed, the build + shield-check state (e.g. "lib clean, parity-check 0"), and what is now JR's to do. If any edit touched a doc (this skill, a design doc, a reasoning doc), **announce it in the summary** — don't fold doc edits silently into a diff. JR's hand-back lists (especially "still pending TL action" items) may reflect a stale snapshot from before TL strips — always verify current state via `grep` before acting on them.

**Always keep a watcher armed.** A `mailbox watch` must be active at all times the TL session is alive — during architect conversation, between escalations, while investigating, even when nothing seems in flight. JR and other TLs can `mailbox send` at any moment; if no watcher is running when that happens, the message sits in your inbox until you `recv`. **The instant after every `mailbox recv` — before reading files, before resolving, before anything else in the same turn — arm a fresh `mailbox watch`.** The previous watcher exited on the fire, and your resolve-the-escalation work can take many tool calls; if you don't re-arm first, you're deaf to a follow-up interrupt during all of it.

**Watch for the next escalation.** After every `mailbox send`, ensure a watcher is running so the next incoming wakes you immediately — don't make the architect type `z` to ferry the signal:
```bash
cd /absolute/path/to/your/worktree && Luz/mailbox/target/release/mailbox watch --as <your-id>
```
Run it with `run_in_background: true`. `mailbox watch` polls the cwd every 500ms (override with `--poll-ms`) for `from-*-to-<your-id>-*.md`. It **blocks until the first new arrival lands, prints its absolute path to stdout, and exits 0** — one watcher, one notification. The harness fires its task-completion notification when the process exits, so you wake up the moment a message arrives. When it fires, `mailbox recv --as <your-id>` (loop if multiple unread piled up), then **arm a fresh `mailbox watch` for the next turn**. The previous watcher is already gone; you don't have stale watchers to kill. **Don't kill watcher PIDs from `ps -ef`** — other TLs' watchers show up globally, and SIGTERMing one fires a spurious task-completion on their side.

**The preventive-tweak habit.** After each escalation, propose one small preventive change (a sentence in the JR-facing migration-drive doc, a scaffolding fix) so that *class* of escalation doesn't recur. The goal is a loop that needs the architect less over time.

**Pre-authorization.** The TL can pre-clear JR for obvious follow-on work ("once you've got X compiling, finalize the parameter list yourself") so JR doesn't bounce back for a second ruling on the same item.

## Guardian Mechanics

### How `guardian.toml` constrains JR

`guardian.toml` selects which shields are active in each mode. The shields it lists are the ones that fire on JR's edits; everything else is silent. Modes typically include a slice mode (placement shields for the slice pipeline), a guard mode (the live set blocking edits during migration — new-definition / renamed / moved / parity shields), and a review mode (post-hoc quality shields). Read `guardian.toml` to know exactly what's live before reasoning about "would Guardian fire" — the active set changes as the migration progresses, and a shield commented out in one mode is not enforcing.

### The shield catalog

The active shield catalog — which shields are live, what they fire on, and the standard resolution for each — is project-specific. See the project's change/migration guide for the list. The TL can't apply the litmus test without knowing it; read it before the first edit.

### Ordination — the TL's prerequisite

The TL lands Guardian-*blocked* edits, which is impossible unless its session is ordained (registered so Guardian skips shield checks for its tool calls). **Ordain the TL session at the start of TL work** — see the `guardian-ordain` skill. The human supplies the port and password; never assume a default port. If a TL edit is unexpectedly blocked, the first thing to check is whether ordination is actually in effect for the current session id.

### `temp_disable` — mechanics and the JR-vs-TL boundary

Guardian exposes a temp-disable for turning a specific shield off on a specific function while a known-good pattern lands.

- **JR issues all temp-disables.** TL **never** issues a temp-disable directly. JR can self-disable any shield on any function — if a TL ruling confirms a denial is a false positive, the TL sends the ruling to JR via `mailbox send --as <tl-id> --to jr` (citing the verdict path and the rationale) and JR applies the temp-disable themselves on the next turn. The mechanism for issuing one is project-local — current canonical path is a `curl` POST to the Guardian server's `/temp-disable` HTTP endpoint with `file_path` / `verdict_file` / `shield_file` / `reason` (and `target_line` to disambiguate when a name resolves to multiple defs); MCP-tool paths have been retired. The TL landing temp-disables is a leak of the role boundary: it bypasses JR's hand on the actual edit and means the architect-reviewable temp-disable comment is attributed to a session that wasn't doing the body work.
- **When JR's self-disable genuinely fails** (verdict-file-not-found, ordination conflict, tool error), JR escalates to TL — and even then the TL's job is to **diagnose why the self-disable failed** (ambiguous request-id prefix, stale verdict path, etc.) and hand JR the working invocation, **not** to issue the disable from the TL session.
- **Stripping temp-disables and curation procedure.** Only the architect can authorize stripping a temp-disable without a corresponding shield change — TL investigates, surfaces, recommends. Per-disable procedure: (1) show the function code, (2) verify parity / no shenanigans, (3) one-line TLDR of what the code does, (4) recommend strip / shield-edit / code-fix. Strip the disable BEFORE dispatching JR to fix the underlying code, so the parity shield can guide the edit. Disable categories: **stale** (refers to deleted code → strip), **legit** (rationale matches code, covered by existing exception → strip on architect ok), **hack** (rationale rationalizes a shortcut → fix the code first, then strip), **context-invisible** (referenced defs the shield can't see → temp-disable IS the right tool, or canonical-edit source to remove the cause).

- **Directive placement.** Temp-disable placement is project-specific (the location Guardian reads for that project's contextified-diff window). See the project's change/migration guide for the exact form.

Prefer fixing the root cause over temp-disabling. If the same divergence keeps forcing temp-disables, that's a signal to amend the shield or the scaffolding, not to disable repeatedly.

### Guardian annotations for source-less definitions

Some projects allow Guardian annotations (e.g. `/* Guardian: disable-all */` or empty audit blocks) on definitions with no source counterpart. Whether annotations are available, what shapes they take, and when each is appropriate is project-specific — see the project's change/migration guide. JR never adds these — JR escalates and the TL adds them.

## Escalation Discipline

- **JR will try to get out of work; TL should keep JR going.** Read escalations skeptically. JR will often escalate unnecessarily if a task seems large, in an attempt to get out of work. Be vigilant and watch for excuses.
- **Hygiene.** JR cites the canonical source origin (the file/line in whatever the project treats as source of truth), not derived/audit-comment locations, so the TL can parity-check against the real source.
- **Verify, don't trust the framing.** The TL always Reads the actual code JR cites, and parity-reviews JR's substantive edits line-by-line against the canonical source (trivial fills → spot-check; body fills or multi-site patterns → end-to-end). When dispatching JR for a multi-site pattern, verify canonical SHAPE at each site, not just one — same-named functions can use different shapes. Also grep the per-pass guide and design doc for keywords from the question — the answer or a direct precedent is often already written down.
- **Don't trust appeal-to-precedent.** "The same pattern was already approved in X" is often JR pointing at a slipped-through bug as license for a new one. Judge against the source, not against prior edits. If both sites are wrong, fix both — don't propagate the divergence.
- **Guardian isn't perfect.** Divergences land without firing any shield. Review every diff against the source even when the shields are silent.

## Commit Protocol

Commit only on the architect's literal **"fire commit"** — which is full commit-and-sync end-to-end (see the verb definition under Architect Interaction Protocol), not "just commit." Stage precise paths (exclude build artifacts and junk; include intentional submodule pin advances). Message format: first line a 1–3-sentence TL;DR that fits on one line (headline, not subject); body describing the changes by file or concern so a reviewer can verify scope without the diff; a trailing bullet list of notable situations (new arcana, Guardian temp-disables added, non-obvious comments, source edits) — omit the list if empty. Use a HEREDOC to preserve formatting. No `Co-Authored-By` trailer unless the architect asks.

**Full `fire commit` sequence (do all of it, in order, before reporting done):**
1. **Leaf submodules first** — for each dirty submodule (and any of its nested submodules), commit there, push to origin per the push-after-pin-advance rule, then come up one level. Commit from leaves up so each level's pin index stays consistent.
2. **Parent repo** — stage source changes plus the now-advanced submodule pins, commit on the working branch.

## What Sync is in Rust

Sync is a Rust marker trait with a precise definition: **`T: Sync` iff `&T: Send`**. That is, T is Sync exactly when a shared reference to T can be safely sent to another thread.

It exists because Rust's `&T` is a SHARED borrow — multiple references can coexist — but T might have interior mutability. Through `&T`, you can call methods like `cell.set(v)` (Cell), `refcell.borrow_mut()` (RefCell), `atomic.store(v)` (Atomic), `mutex.lock()` (Mutex). So `&T` doesn't promise the data won't change — only that YOU can't mutate it directly; interior mutability might.

Different interior-mutability types have different concurrency safety:
- **Cell, RefCell**: unsynchronized interior mutability. Two threads accessing concurrently → data race. These types are `!Sync`.
- **Mutex, RwLock, atomics**: synchronized interior mutability. Two threads accessing concurrently is fine; the primitive handles it. These types are `Sync`.
- **No interior mutability** (a plain struct of primitives): trivially safe; `Sync`.

Auto-derived: `T: Sync` iff all fields are Sync. Standard auto-trait propagation.

## Why Rust needs Sync

Three concrete use cases where Sync is what the type system checks:

1. **`Arc<T: Send + Sync>`** — Arc has multiple owners across threads; each owner can pass `&T` to its thread; cross-thread shared access requires Sync.
2. **`tokio::spawn(future)` where `future` captures `&x`** — for the future to be Send, the captured `&x: Send` must hold, which requires `x`'s type: Sync.
3. **Generic bounds like `fn parallel_iter<T: Sync>(slice: &[T])`** — caller code that processes a slice in parallel needs Sync on element type.

Without Sync, Rust's type system couldn't distinguish "shared borrow safe to send to another thread" from "shared borrow that would race." Cross-thread sharing safety would be lost.

The information Sync carries is specifically: **does this type's interior mutability (if any) synchronize across threads?** For pure value types (no interior mutability), Sync is trivially true. For interior-mutability types, Sync is true iff the mutation is synchronized.

## What read groups do in Vale that subsumes Sync's role

Vale's read group annotation says: **"no unsynchronized mutation through references in this group."** Typechecker-enforced at the access level: Cell.set, RefCell.borrow_mut, etc. are inaccessible through read-group references. Synchronized methods (Mutex.lock, atomic.store, channel.send) ARE accessible.

This is **stronger** than Rust's `&T`: Rust's `&T` permits unsynchronized interior mutation; Vale's `&read T` blocks it.

The consequence for cross-thread safety: in Vale, ANY reference in a read group is cross-thread-shareable. The group annotation is the safety mechanism. The underlying type's interior-mutability situation doesn't matter Vale-side, because Vale's typechecker is preventing the dangerous accesses regardless.

So Vale-source-internally:
- "Is this reference safe to share across threads?" → "Is it in a read group?" — answered by group annotation.
- No per-type property needed. The type's Sync-ness (if it had one) is irrelevant.
- A Vec<i32> can be in a read group → safe to share. A Vec<Cell<i32>> can be in a read group → also safe to share (Cell.set isn't callable through read-group ref).

**This is genuinely simpler than Rust's model.** Rust needs Sync because `&T` allows interior mutation, so type-level analysis is necessary. Vale's read group rules out the dangerous accesses at the group level, so the type-level analysis isn't needed.

## What Sync solves that read groups don't (the actually-honest part)

**One thing.** At the Vale↔Rust boundary, Rust's typechecker uses Sync. When Vale exports a reference to Rust, Rust's type system wants to know `T: Sync?` to decide if `&T` can cross threads.

- **If Rust's bare `&T` projection is the only export form**: Rust needs to see T: Sync. Vale would need to emit a Sync claim. Internally Vale would either auto-derive it (per-type analysis) or get it from somewhere.
- **If Vale uses wrapper types (ValeImm) for cross-thread export cases**: the wrapper carries `unsafe impl Send` explicitly. Rust's Sync check doesn't apply to the wrapper. Bare `&T` projection works only for single-thread use; Rust callers wanting cross-thread share use the wrapper.

So Sync's role-at-the-boundary collapses to: "what does Vale tell Rust so Rust's typechecker can decide cross-thread safety?" The wrapper mechanism is an alternative to emitting Sync claims.

**The wrapper-based approach really does work without Sync.** Concrete implications:
- Bare `&T` projection from Vale to Rust never carries a Sync claim. Rust treats it as `!Sync` (no Sync impl). Rust callers can use it in single-thread contexts only.
- Vale-side seamless-fearless surfaces (pure functions, parallel blocks) produce ValeImm wrappers when emitting references to Rust. The wrapper has `unsafe impl Send + Sync` justified by Vale's read-group analysis + bounded lifetime.
- For cross-thread share from Rust, Rust callers must obtain the reference through a Vale pure/parallel block. Outside those contexts, references are single-thread-only from Rust's view.

The cost of this approach: Rust callers can't do `tokio::spawn(async move { use(&vale_value); })` with a plain Vale-exported `&T`. They'd need to wrap the access in a Vale pure/parallel block first, then use the wrapper. Real ergonomic restriction but a clean architectural line.

**Vale really doesn't need Sync if you're OK with that restriction.** The honest answer to your question.

The case where you might want Sync at the boundary regardless: you want Rust callers to be able to use plain `&T` cross-thread for the common case (when T has no interior mutability or only synchronized interior mutability, which is most Vale types). Without Vale emitting a Sync claim, even safe cases require the wrapper detour.

Three positions, ordered by user-facing ergonomics:

- **(β) Vale auto-derives Sync at typing pass.** Stub_gen emits `unsafe impl Sync` claims for Vale types whose fields are all Sync. Rust callers can use bare `&T` cross-thread for safe cases. Honest because Vale's analysis is real; ergonomic because no wrapper detour needed.
