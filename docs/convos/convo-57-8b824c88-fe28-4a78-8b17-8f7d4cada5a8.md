**TLDR of how it works:**

It's the repo's only sanctioned path for bulk edits (`sed` and `perl -pi` are outlawed; under ~40 files, just use the Edit tool). Binary at `Luz/safe-script-runner/target/release/safe-script-runner`, three subcommands: `review`, `apply`, `abandon`.

You write a pure stdin→stdout Python transform at `./tmp/scripts/<name>.py` — no file I/O, no subprocess, no `exec`/`eval`. Then, one file at a time:

1. `review <script> <SRC>` — runs the transform, prints the **full** stderr and diff, and writes a marker at `./tmp/working/.current-review` holding the script path, the src path, and a SHA-256 of the output.
2. `apply <script> <SRC>` — re-runs, checks the marker's `(script, src)` and hashes still match, backs up `<SRC>` to `./tmp/backup/<ts>/`, then `mv`s the result over the source and clears the marker.

Two invariants do the real work:

- **Single marker.** Only one review can be pending. Reviewing a second file while one is unapplied is refused, which makes batch-review-then-batch-apply physically impossible — the only achievable order is review A → apply A → review B → apply B.
- **Hash binding.** If the script or the source changed between review and apply, apply refuses and you must re-review.

Together they guarantee the human's "go" was given against the exact diff that lands. Supporting rules: `apply` always needs explicit authorization first (review is read-only and doesn't), you must write out `Issues I see in the diff:` after each review, and it's deliberately serial — the skill has a case study of a past session getting blocked on a chained loop and then inventing a `python3` driver to bypass the tool, which is the failure mode it's guarding against.

Why it doesn't fit slice 8: it rewrites a file's *contents* in place at the same path. A rename changes the path, which the tool has no concept of.
