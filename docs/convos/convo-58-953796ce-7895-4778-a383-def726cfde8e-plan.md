# Fill `as_subtype_macro`'s result coords, and let an unrelated downcast report

## Context

`generate_function_body_as_subtype` (`FrontendRust/src/typing/macros/as_subtype_macro.rs`) carries two
adjacent `unimplemented!()`s at `:61-62`:

```rust
let success_coord = unimplemented!();//KindT::new(result_ownership, RegionT::Default, target_kind);
let fail_coord = unimplemented!();//KindT::new(result_ownership, RegionT::Default, incoming_kind);
```

It is now the joint-largest simple cluster at **10 tests**. Six are `compiler_project_tests::typing_pass_*`
whole-program tests that reach it only by scouting `as.vale`; four are about downcasting for real.

`as.vale` declares the operation in two flavours, and that is what shapes the fix:

```vale
func as<SubType, SuperType>(left &SuperType) Result<&SubType, &SuperType>
func as<SubType, SuperType>(left  SuperType) Result< SubType,  SuperType>
```

So `as` is **wrap-preserving**: each arm of the `Result` refers to its citizen exactly the way the
parameter refers to its own. The commented Coord code read a `result_ownership` off the parameter and
reapplied it; under the onion the shape *is* the parameter's type, which is why `incoming_ownership`
at `:50` is already commented out and goes away with this change.

## Step 1 — build the two coords from the parameter's own shape

`FrontendRust/src/typing/macros/as_subtype_macro.rs`, replacing `:52-62`:

```rust
let incoming_coord = param_coords[0].tyype;
// The declared param is `&SuperType` or `SuperType`, so the citizen is under whatever wraps the
// signature wrote. is_parent and ISuperKindTT below want the citizen, not the reference to it.
let incoming_kind = peel_all_references(incoming_coord);

// `as` preserves the parameter's shape into both arms of the Result: the success arm refers to the
// SubType the way the param refers to its own citizen, and the failure arm hands the param back
// unchanged.
let success_coord = replace_value_type_in_ref(self.typing_interner, incoming_coord, target_kind);
let fail_coord = incoming_coord;
```

Reuse, not new code — both helpers exist and are documented for exactly this:

- `replace_value_type_in_ref` (`typing/templata_compiler.rs:101`) — *"Rebuilds `full_type_with_refs`'s
  chain of reference layers around `new_value_type` … Used where a type's shape is fixed but the
  citizen inside it changes."* Regions carry over layer for layer; a bare input returns the new value
  type unchanged, which is precisely the owning overload.
- `peel_all_references` (`typing/templata_compiler.rs:86`).

`fail_coord` is written as `incoming_coord` rather than
`replace_value_type_in_ref(interner, incoming_coord, incoming_kind)` because the two are equal by
construction — rebuilding a type's own wraps around its own peeled citizen is the identity. The
comment says so, so nobody re-derives it.

**This also closes defect 3.** `ISuperKindTT::try_from` at `:73` admits only `Interface` /
`KindPlaceholder` (`types/types.rs:570`), so today it rejects the borrowed overload's
`BorrowRef(Interface(..))` and hits `panic!("vwat")`. Peeling `incoming_kind` fixes that in the same
stroke. `target_kind` needs no peel — it comes from the function name's template args
(`local_name.template_args().first()`), which bind citizens; if that ever changes, `:69`'s
`ISubKindTT::try_from` catches it loudly.

**A built-in verifier for this step:** `:65` already asserts `result_coord == maybe_ret_coord`. If the
shapes we build disagree with the declared return type, that panics with "Bad result coord" rather
than producing a wrong `Result`. Getting past it *is* the evidence the construction is right.

## Step 2 — an unrelated downcast must report, not panic

Recommended in the same change, because one of the ten tests needs it and it is otherwise the
immediate next blocker. At `:86-88`:

```rust
IsParentResult::IsntParent(_) => panic!("vwat"),
```

`report_when_downcasting_between_unrelated_types` (`after_regions_error_tests.rs`) expects
`ICompileErrorT::CantDowncastUnrelatedTypes`, which already exists
(`compiler_error_reporter.rs:30`) with a live humanizer arm (`compiler_error_humanizer.rs:179`,
*"Can't downcast `X` to unrelated `Y`"*). Return it with `source_kind: incoming_kind`,
`target_kind`, and the range.

**The one non-mechanical part:** the payload types do not line up. `IsntParent` carries
`candidates: Vec<IResolvingError>` (`citizen/impl_compiler.rs:56`) while the error variant wants
`candidates: &'t [FailedSolve<…>]`. Each `IResolvingError::ResolvingSolveFailedOrIncomplete(f)`
holds the `FailedSolve`; unwrap those and drop any other variant, then
`typing_interner.alloc_slice_from_vec`. This is the same unwrap the abstract-body reporter does for
`FindFunctionResolveFailure`, so follow that shape rather than inventing one.

If this step is dropped, step 1 still stands — the nine other tests advance and the negative test
just moves from `:61` to `:87`.
