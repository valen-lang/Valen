## What a preliminary solve is

`evaluate_generic_virtual_dispatcher_function_for_prototype_solving` runs **two** solves, and they answer different questions.

**The preliminary solve asks: given the impl's interface as the virtual parameter's type, which of the abstract function's generic params does that determine?** It runs the abstract function's own rules plus the sends, and whatever concludes is a genuine pin. That's Generics.md's CDFGI (Step 2) — "take the original abstract function and try to compile it given the dispatcher interface as the first parameter."

**The defining solve then compiles the dispatcher for real**, seeded with those pins via `placeholder_initial_knowns_from_function`, plus a fresh `dis$N` placeholder for anything the preliminary solve *didn't* pin.

You need the census before the compilation, because you can't compile a generic function until you know which of its parameters have values and which need placeholders standing in for "any type."

## The setup

An interface's abstract function has to be compiled once for each struct that implements it, to build the switchboard. When the compiler does that, it pretends the receiver is that particular implementer's type and asks what it can figure out.

```vale
interface Opt<T> { }
struct Some<T> { value T; }
impl<I> Opt<I> for Some<I>;

abstract func map<T, R>(self &Opt<T>, converter Converter<T, R>) Opt<R>;
```

`map` has two generic letters, `T` and `R`.

## The preliminary solve is a trial run

The compiler says: "the receiver is going to be an `Opt<something>`. Let me plug that in and see which letters fall out."

It plugs `&Opt<␣>` into `self &Opt<T>` and gets:

- **`T` — learned.** `T` is whatever's inside the `Opt`. The receiver told us.
- **`R` — not learned.** `R` only shows up in the `converter` parameter and the return type. Nothing about the receiver mentions `R`, so there's nothing to deduce it from.

That's the whole job of the preliminary solve: **sort the letters into "the receiver told me" and "the receiver said nothing."**

## Why `R` is stuck

The compiler isn't at a real call site here. Nobody has written `map(myOpt, myConverter)` yet. It's building the switchboard ahead of time, and the *only* thing it knows about is the receiver — the thing being dispatched on. There is no converter argument to look at.

In the code that's literally what it does: it makes a list of arguments where every slot is empty except the receiver's.

## What happens next

The real compile then needs a value for both letters. `T` has one. `R` doesn't, so the compiler has to invent a stand-in — a "some type, I don't know which" token — and compile the function against that. It's the same trick used for any generic function: compile once against a placeholder instead of once per real type.

That invention step is the line that still says `panic!("implement: create placeholder for missing preliminary inference")`. It fires whenever a letter comes back unlearned.

## Why our test stopped hitting it

```vale
interface MyOption<T> { }
// auto-generated: abstract func drop<T>(this MyOption<T>)
```

`drop` has one letter, `T`, and it appears right there in the receiver. So the receiver tells us everything, nothing is left unlearned, and the unwritten placeholder step never runs.

Before you wired the sends, the receiver's type was being thrown away — so even `T` came back unlearned, and it hit that panic. Now the receiver's type actually arrives, `T` is learned, and it sails past.

A `map`-shaped function would still hit it, because `R` genuinely can't be learned that way.

That's it. It's a lookup, not the real compilation — it's figuring out which letters it already knows before it starts.

## 🤖 Claude

Confirmed in the code. Your intuition is close, and the one place it's off is worth knowing.

## They're not the same function

**The abstract function** is the declaration — `abstract func drop<T>(virtual this MyOption<T>)`. It's compiled once, generically, with its own placeholders (`drop$0`). It has no body. It's the thing users call.

**The dispatcher** is a separate function the compiler mints, with its own name and its own placeholders (`dis$0`). Its name literally records which impl it belongs to — `odis{impl:98}` in the shorthand. It holds the switchboard.

And there's **one dispatcher per impl**, not one per abstract function. `look_for_override` (`edge_compiler.rs:250`) takes both an `impl_t` and an `abstract_function_prototype`, and gets called once per pair. So `MyOption` with two implementors produces two dispatchers for `drop`.

That's the part your model was missing. Generics.md's reason is a good one: given

```vale
impl<I, J> ISpaceship<int, I, J> for Raza<I, J>;   // note the int
impl<H>    ISpaceship<H, H, H>   for Enterprise<H>; // note they're all the same
```

Raza's dispatcher knows its first type argument is `int`. Enterprise's knows all three are the *same* type. Those are different facts, so they can't be one function — "Raza and Enterprise have some assumptions about their generic args, so we'll need different conceptual functions for them."

Then the abstract function **calls** the dispatcher (`AFCTD`). Two functions, a call between them, not one function with a body.

## Who's asking the question

The itable builder. `compile_i_tables` walks every interface, then every impl of it, then every abstract method — and for each of those combinations calls `look_for_override`, which is what needs an answer before it can go looking.

The thing being *solved* is the abstract function's rules. The thing being *built* from the answer is the dispatcher. So:

> The compiler takes the abstract function's rules and asks: **if the receiver were this impl's interface, what would my type parameters be?**

The answer becomes the dispatcher's starting knowledge. Generics.md calls it "an alternate way of compiling a function" — same declaration, compiled a second time, per impl, with `dis$` placeholders instead of its own.

## Concretely

For `impl<I> Opt<I> for Some<I>` and `abstract func map<T, R>(self &Opt<T>, f &IFunction1<&T, R>) Opt<R>`:

1. The itable builder is on the `Some` impl and the `map` method.
2. It takes the impl's interface and rewrites it in dispatcher terms: `Opt<dis$0>`.
3. It hands that to `map` as the receiver — and *only* the receiver; the `f` slot is passed as "nothing."
4. `map`'s rules run. `&Opt<T>` versus `&Opt<dis$0>` gives `T = dis$0`. Nothing mentions `R`, so `R` comes back unknown.
5. Now build the dispatcher: `T` uses the value it got, `R` needs a fresh cutout.
6. With the dispatcher's environment in hand, look up `Some`'s real `map` and record it in the itable.

Step 4 is the preliminary solve. Step 5 is the defining solve — and the missing cutout in step 5 is the panic still sitting at `function_compiler_solving_layer.rs:610`.

## 🤖 Claude

Two good questions, and the first one has a "no" that's worth being precise about.

## No — the routing is a table, not the abstract function

What this pass actually builds is the **itable**: for each interface, for each implementing type, an `EdgeT` whose `abstract_func_to_override_func` maps each abstract method to the override to call. So the structure that decides "which implementation runs" is a lookup keyed on the concrete type — the classic vtable shape. The abstract function isn't a `match` over dispatchers.

The dispatcher isn't something you route *to* at runtime either. It doesn't survive as a function in the output; it's a compile-time device. It exists to give the compiler a vantage point from which to resolve one impl's override, and to give the instantiator something to substitute per edge.

Where the "call" language in the docs comes from: in the typing pass the abstract function is modeled as calling the dispatcher (`AFCTD`), which is what lets the instantiator later say "for this concrete instantiation, which edge applies, and therefore which dispatcher's substitutions do I use." That's a compile-time resolution, not a runtime branch.

## Yes — a dispatcher's job is to find that impl's override

That's exactly what it's for, and the evidence is what it produces. `OverrideT` (ast.rs:96) carries:

```rust
pub dispatcher_call_id: IdT,
pub case_id: IdT,
pub override_prototype: PrototypeT,   // ← the impl's actual function
```

`override_prototype` is `Some`'s real `map`, or `Raza`'s real `launch`. The dispatcher exists to make that lookup possible and correct, and then it's recorded in the edge.

The reason the lookup needs a dispatcher at all is that the override has requirements the abstract function can't see. Generics.md's `ONBIFS` is the worked case: `bork` on `BorkForwarder<Lam>` requires a `__call(&Lam)int`, and the abstract `bork(&Bork)` knows nothing about any `Lam`. Resolving the override from the abstract function's own environment fails. So the compiler builds an environment that's the abstract function's, but rephrased for *this* impl — carrying the impl's type arguments and the bounds that come with them — and resolves from there.

## The whole shape, in order

```
interface Opt<T>              ← declares map
abstract func map<T,R>(...)   ← the thing you call; no body

for each impl of Opt:
   ├─ impl<I> Opt<I> for Some<I>   →  dispatcher #1  →  finds Some's map
   └─ impl<I> Opt<I> for None<I>   →  dispatcher #2  →  finds None's map

itable: Opt ─┬─ Some → edge { map → Some's map }
             └─ None → edge { map → None's map }
```

Each dispatcher handles one impl and produces one entry. The itable is assembled from all of them, and *that's* what does the routing.

So your original instinct — "the dispatcher is the body of the abstract function" — is the right intuition pointed at the wrong granularity. There's no single body; there's one dispatcher per impl, each producing one row of the table, and the table is the switchboard.

|---|---|---|
| **abstract function** | the entry point users call | only "this is an `Opt<something>`" |
| **edge table row** | one per (implementing type, method) | the runtime answer: it's actually a `Some` |
| **dispatcher** | one per (impl, method) | the type-argument story for *that* impl |
| **override** | the impl's real function | the actual code |

}

## Your instinct is right, and it splits the language world in two

This is a **generic virtual method** — a virtual method with type parameters of its own, beyond the receiver's.

| language | allowed? | why |
|---|---|---|
| **C++** | no, hard rule | a template member function cannot be `virtual` |
| **Rust** | not through `dyn` | a generic method makes a trait non-object-safe; fine for static dispatch |
| **Java** | yes | erasure — `<R>` doesn't exist at runtime, so one vtable slot serves every `R` |
| **C#** | yes | reified generics, the runtime specializes on demand |

The dividing line is exactly *how the language implements generics*. Erase them (Java) or specialize at runtime (C#) and it's free. **Monomorphize them and it's hard**, because each `R` needs its own compiled function, so a single vtable slot can't serve them all.

Vale monomorphizes. So it lands on the hard side, with C++ and Rust.

## Why it's nonetheless workable here

Rust's objection is that it compiles crates separately — it can't know which `R`s exist, so it can't bound the vtable. Vale compiles the whole program, so the instantiator sees every call site and the set of `R`s actually used is finite and enumerable.

That's why `R` becomes a **dispatcher placeholder** rather than being erased: the dispatcher is generic in `R`, and monomorphization stamps one per `R` the program actually uses — the same machinery as `dis$X` in the doc's `AFCTD` walkthrough, just for a parameter that came from the method instead of the impl.

## Which reframes the missing line

I've been calling `panic!("implement: create placeholder for missing preliminary inference")` a leftover to-do, and mechanically it is one. But what it gates is **generic virtual dispatch** — the feature C++ refuses outright and Rust refuses through `dyn`. ```

So "isn't solvable" isn't a failure — it's the answer that means *this one stays generic*, and the correct response is to make a placeholder. That's why the panic is a to-do rather than a bug: someone wrote the pinned half and left the unpinned half for later.

One nuance worth having, since "figure out what `T` is" can suggest a concrete type: what comes back for `T` is usually itself a placeholder — `dis$0` — because the dispatcher is compiled once for all `Some`s, not per `Some<int>`. So both `T` and `R` end up as stand-ins in the finished dispatcher. The difference is *where the stand-in comes from and what later fills it in*:

- `T`'s comes from the impl, so when the program is monomorphized, dispatching on a `Some<int>` fills it with `int`.
- `R`'s would be minted by the dispatcher itself, and gets filled in by whatever the caller asked for.

Raza is the case where a pin really is concrete — `impl<I,J> ISpaceship<int, I, J>` gives `X = int` outright, no placeholder.

## 👤 User

is R an "independent" rune?

## 🤖 Claude

No — and the contrast is a clean one, because they're the two different things the interface can fail to determine.

**Independent runes are the *impl's* runes.** Milano's `ZZ`:

```vale
impl<I, J, K, ZZ> ISpaceship<I, J, K> for Milano<I, J, K, ZZ>;
```

Solve that impl given only `ISpaceship<dis$0, dis$1, dis$2>` and `I`, `J`, `K` fall out while `ZZ` doesn't. `ZZ` is independent; the rest are dependent. The doc computes this in ImplCompiler and remembers it per rune.

**`R` is the *abstract function's* rune.** It's unpinned for a different reason: not "the impl has a parameter the interface doesn't cover," but "the method has a type parameter its receiver doesn't mention."

## The difference that matters

Who supplies the value, and where it's bound:

```vale
    <ZZ> milano &Milano<X, Y, Z, ZZ> => launch(milano, bork)
//  ^^^^ bound by the arm
```

`ZZ` is bound *inside the match arm* — "there exists some `ZZ` such that this value is a `Milano<X,Y,Z,ZZ>`." Nobody chooses it; it's whatever the value at hand happens to be, and it's discovered by dispatching.

`R` is bound on the **function**, and the caller chooses it. `map(myOpt, intToStr)` picks `R = str`; nothing about the value being a `Some` has any say.

## Which shows up as

| | `ZZ` (independent) | `R` (unpinned method param) |
|---|---|---|
| belongs to | the impl | the abstract function |
| bound where | the match arm | the dispatcher's signature |
| placeholder family | `case$N` | `dis$N` |
| filled in by | the concrete type you dispatched on | the caller |
| in the dispatcher's `templateArgs`? | **no** — the doc is explicit, "there's no `dis$ZZ` in here" | **yes** — otherwise the Instantiator can't substitute it |

That last row is the practical tell, and it's what the comment at `edge_compiler.rs:393` is about: unpinned method params like `R` must appear in the dispatcher's `templateArgs`, because `assemble_placeholder_map` zips those against the concrete args at monomorphization. A placeholder missing from that list can't be substituted and trips a `vassertSome` later.

So both are "the interface didn't determine it," but one is existential and discovered by dispatch, and the other is universal and supplied by the caller.

## 👤 User

so what does the preliminary solve actually do?

---

## 🤖 Claude

Mechanically, four steps, and only the last one produces anything that survives.

1. **Take the abstract function's own rules** — its declaration rules, filtered to the definition-side ones (`function_definition_rules`).

2. **Add the one fact the impl supplies**: the virtual parameter's type is this impl's interface, `Opt<dis$0>`. That's the send — seed a rune with the interface, and an `Equals` tying it to the parameter's type rune.

3. **Run the solver** until it stops making progress. It works out the whole receiver type, the macro runes, whatever else follows.

4. **Look up each of the abstract function's generic params in the conclusions.** Present → that's the value. Absent → it needs a fresh placeholder.

Step 4 is the entire output. Everything else is thrown away — the rules aren't reused, the other conclusions aren't kept. All that's carried forward is `placeholder_initial_knowns_from_function`, the list of "here's what each type parameter starts as," which the real defining solve is then seeded with.

## Why it has to be a separate pass

Compiling a generic function means seeding its type parameters first and *then* solving. But you can't seed them until you know which ones already have values from the impl — seed a placeholder over `X` when the impl said `X = int` and you've destroyed the thing that made this dispatcher specific to Raza.

So: cheap pass to find out, then the real pass.

That's the same move as `IRAGP` elsewhere in the doc — "when we're compiling the functions, we hand in some placeholders which immediately conflict with these rules; for that reason, we do some solving before filling in any placeholders." The preliminary solve is the dispatcher's instance of it.

## In one sentence

It converts *"the receiver is this impl's interface"* into *"here's what each of the abstract function's type parameters starts out as"* — and the sends are what carry the receiver in, which is why nothing worked until they were consumed.

## 👤 User

why is it useful to know that T = dis$0 and nothing for R?

## 🤖 Claude

Because the dispatcher can't be compiled until every type parameter has a value, and the two answers require opposite treatment.

**`T = dis$0` is information you'd otherwise lose.** Raza is the vivid version:

```vale
abstract func launch<X, Y, Z>(self &ISpaceship<X, Y, Z>, bork X);
impl<I, J> ISpaceship<int, I, J> for Raza<I, J>;
```

The preliminary solve says `X = int`. So the dispatcher's second parameter becomes `bork int`, and its bound `drop(X)void` becomes `drop(int)void`.

Now the payoff: the override you're trying to find is

```vale
func launch<Y, Z>(self &Raza<Y, Z>, bork int) { ... }
```

It takes an `int`. If you'd skipped the preliminary solve and just minted a fresh placeholder for `X`, you'd be looking for `launch(&Raza<..>, bork dis$0)` — and you wouldn't find it. The whole point of the exercise is to resolve that override, and it only resolves if the parameter types are phrased the way the impl forced them.

**"Nothing for `R`" is also information.** It says: don't wait for a value, none is coming — mint a stand-in and keep the dispatcher generic in it. Guess wrong in either direction and you break something:

- Treat a pinned one as free → you lose the impl's constraint, and the override lookup fails (the Raza case above).
- Treat a free one as pinned → you'd have to invent a value, and you'd compile a dispatcher that only works for one `R` instead of all of them.

So the preliminary solve is the compiler sorting the type parameters into "the impl already decided this" and "this stays open," because those are the only two things it can do with them, and doing the wrong one is silently wrong rather than loud.

**The goal:** for every type that implements an interface, the compiler needs to know which real function to run for each method. That's the lookup table behind `x.map(...)`.

## There is no filter

`get_candidate_banners` (`overload_resolver.rs:147`) collects candidates **by name only**, from three sources: the calling env, each parameter's env, and placeholder extra envs. No arity check, no wrap-chain check, no value-type-template check — nothing that looks at the arguments at all beyond using them to find envs.

Then `find_potential_function` does this:

```rust
for candidate in candidates.iter() {
    match self.attempt_candidate_banner(...)? {
        Ok(s)  => successes.push(s),
        Err(e) => failed_to_reason.push((*candidate, e)),
    }
}
if successes.is_empty() { ...FindFunctionFailure... }
else if successes.len() == 1 { win }
else { self.narrow_down_callable_overloads(...) }   // tiebreakers
```

That's the per-candidate solve loop, plus a tiebreaking layer at the end. It is exactly what filter-is-final is designed to replace, and the handoff says so in as many words: *"A per-candidate phases-0–3 loop with 4–5 on the winner is the shape to expect if you reason from the current code — `attempt_candidate_banner` still works that way — but it is what filter-is-final replaces."*

So every `drop` in `drop.vale` is a candidate, and each one gets fully solved.

## And even if the filter existed, it wouldn't be what excludes this one

Worth knowing, because it's counterintuitive. Of the filter's three inputs:

- **arity** — the blanket takes one parameter, so does the call. No help.
- **wrap chain** — the parameter is `[BorrowRef]`, the argument is `[]`. But the filter compares *up to adjustment*, and bare→borrow is an admissible auto-ref. So it passes.
- **value-type template** — the blanket's value type is a bare rune, which accepts anything. No help.

The mechanism that excludes it is **namespaces**: the blanket belongs to `&T`'s namespace, which lives in a `borrow.vale` that doesn't exist yet, and a lookup peels the argument's value type so it searches `int`'s namespace and never reaches it. The handoff uses this exact pair as its worked example. Namespaces aren't implemented either — `find_function` resolves an imprecise name against the environment.

So two ruled mechanisms would each keep this candidate out, and neither is built.

## Which makes the actual bug smaller than it looks

Look at the loop's shape: `attempt_candidate_banner` returns `Err(reason)` for a candidate that doesn't fit, and it lands in `failed_to_reason`. **The design today already expects mismatched candidates, and rejects them by failing their solve.** That's how the blanket was disposed of before — `params_match` rejected it after solving.

So the candidate's presence isn't the defect. The defect is that its solve now *panics* instead of returning `Err`. Sends made the mismatch surface earlier, inside the solve, at a spot written as `unimplemented!()` because nothing had ever reached it.

That's the whole fix: the peel arm should return a solve failure so the candidate loses normally. It doesn't need the filter, it doesn't need namespaces, and it doesn't need phase 0 — those change *which* candidates arrive, not what happens when one doesn't fit.

## The dual of the assert we already have

`make_solver_state_solver` asserts *every rule's runes are in `rune_to_type`* — the one we improved this afternoon. The missing half is its mirror:

> **every param's `full_type_rune` and `value_type_rune` are in `rune_to_type`**
